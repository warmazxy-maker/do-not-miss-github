# 个人能力系统双标签改造开发指南

## 1. 背景

当前系统在用户完成学习活动后，会由 LLM 抽取能力标签，并执行三种操作：

1. 给已有标签加分；
2. 与语义相似标签融合；
3. 无法融合时创建新标签。

现有方案的问题是：系统依赖“语义相似度”判断标签是否融合，但很多标签实际上不是同义关系，而是上下位关系。

例如：

```text
Java基础
Java程序设计
Java网络编程
Java高并发
Java线程池
```

这些标签互不等价，因此很难触发融合，最终导致用户长期能力页面中出现大量并列、细碎、含义重叠的标签。

新的系统需要将用户能力拆成两个维度：

```text
知识与技术标签：用户掌握了什么
职能能力标签：用户能够完成什么类型的工作
```

暂时不增加行业维度。

---

## 2. 改造目标

### 2.1 知识与技术标签

用于描述用户长期掌握的知识领域、技术体系、学科或语言。

示例：

```text
Java
数字电路
数据库
计算机网络
概率统计
机器学习
日语
合同法
摄影
```

知识标签需要保持较粗粒度。

以下内容不应直接成为个人主页一级知识标签：

```text
Java线程池
Java网络编程
Spring事务传播
数字电路中的触发器
日语N2听力
Redis缓存穿透
```

这些细粒度内容应保存为：

- 子知识点；
- 学习记录；
- 能力证据；
- 标签详情中的细分内容。

例如：

```text
Java
├── 基础与面向对象
├── 集合与泛型
├── 并发编程
├── 网络编程
├── JVM
└── Spring生态
```

个人主页只展示 `Java`。

### 2.2 职能能力标签

用于描述用户能够承担的工作职能。

示例：

```text
后端开发
前端开发
嵌入式系统开发
电子系统设计
数据分析
软件测试
产品管理
游戏系统设计
财务分析
市场研究
```

职能能力必须从受控的标准职能桶中选择。

之前整理的约 400 个职能桶作为标准种子库，单独存放，不在本指南中重复输出。

职能标签不允许由 LLM 随意创建。无法匹配时应返回：

```text
NO_MATCH
```

或：

```text
REVIEW_REQUIRED
```

后续由管理员决定是否增加新的标准职能桶。

---

## 3. 非目标

本次开发暂时不实现以下内容：

- 不增加行业标签；
- 不判断用户属于汽车、船舶、金融、医疗等具体行业；
- 不把当前学习路径图谱改造成个人全局能力图谱；
- 不修改路径内部原有的细粒度能力图谱逻辑；
- 不要求一次性建立覆盖全世界知识的完整知识库；
- 不允许单纯看课程就获得明显的职能能力分数。

路径图谱和个人能力系统需要继续保持独立：

```text
路径图谱：描述用户在当前学习路径中学到了哪里
个人能力：描述用户长期掌握了什么、能够做什么
```

## 4. 页面结构

个人能力页面展示两组标签。

### 4.1 核心职能

放在上方，优先展示用户当前最强的工作能力。

示例：

```text
核心职能

后端开发        黄金 Lv.6
智能体系统开发  白银 Lv.4
软件测试        白银 Lv.3
数据分析        青铜 Lv.2
```

默认展示分数最高的 6～8 个职能，剩余内容通过“查看全部”展开。

### 4.2 知识与技术

放在核心职能下方。

示例：

```text
知识与技术

Java          黄金 Lv.7
数据库        白银 Lv.5
计算机网络    白银 Lv.4
大语言模型    白银 Lv.4
日语          青铜 Lv.3
```

默认展示 8～12 个。

### 4.3 标签详情

点击职能标签后，展示：

```text
后端开发 Lv.6

支撑知识：
Java、数据库、缓存技术、计算机网络

能力证据：
- 完成订单服务开发
- 实现Redis库存预扣
- 通过并发编程项目验收
- 完成接口性能优化

最近更新：
2026-07-29
```

点击知识标签后，展示：

```text
Java Lv.7

细分知识：
- 基础与面向对象
- 集合与泛型
- 并发编程
- JVM
- 网络编程

相关职能：
- 后端开发
- 测试开发
- 分布式系统开发

学习证据：
- Java并发课程
- 秒杀系统项目
- JVM测验
```

## 6. 能力处理流程

不要继续使用：

```text
新标签
→ 与历史标签计算语义相似度
→ 相似则融合
→ 不相似则新建
```

改为以下流程：

```text
学习活动
↓
生成标准学习证据
↓
提取细粒度知识点
↓
归入粗粒度知识标签
↓
判断证据是否具备职能更新资格
↓
从标准职能桶中召回候选
↓
LLM选择0～3个职能桶
↓
计算分数并保存证据
```

## 7. 第一阶段：学习证据标准化

输入需要包含：

```json
{
  "activity_type": "MICRO_PROJECT",
  "title": "Java秒杀系统",
  "description": "使用Java、Redis和消息队列实现库存预扣、重复下单拦截和超时回滚",
  "difficulty": 4,
  "completion_status": "PASSED",
  "performance_score": 0.88,
  "path_id": "optional",
  "node_id": "optional",
  "project_output": "optional",
  "test_result": "optional"
}
```

不同来源需要统一转换成该结构。

必须保证同一个学习活动只能生成一次能力更新。建议使用：

```text
user_id + source_type + source_id
```

作为幂等键。

## 8. 第二阶段：知识标签归类

### 8.1 提取内容

LLM 首先抽取：

- 核心知识领域；
- 细粒度知识点；
- 本次活动训练了什么；
- 是否只是工具被动出现。

示例输入：

```text
用户使用Java、Redis和消息队列完成库存预扣与超时回滚。
```

示例输出：

```json
{
  "knowledge_candidates": [
    {
      "bucket_name": "Java",
      "fine_skills": ["并发编程", "服务端业务开发"],
      "importance": 0.9
    },
    {
      "bucket_name": "缓存技术",
      "fine_skills": ["Redis", "库存预扣", "原子操作"],
      "importance": 0.85
    },
    {
      "bucket_name": "消息队列",
      "fine_skills": ["异步消息", "超时回滚"],
      "importance": 0.75
    }
  ]
}
```

### 8.2 知识标签粒度规则

知识标签必须满足：

1. 能长期积累；
2. 能容纳多个不同子知识点；
3. 不是单节课程名称；
4. 不是一次项目名称；
5. 不是过细的技术机制；
6. 用户能够自然地说“我掌握这个领域”；
7. 名称通常为 2～10 个汉字或稳定的技术名称。

正确：

```text
Java
数字电路
数据库
计算机网络
概率统计
机器学习
日语
```

错误：

```text
Java高并发
Java线程池
Redis缓存穿透
N2听力第一章
D触发器实验
```

### 8.3 知识标签匹配方式

知识标签是个人能力档案，不建设全局知识 taxonomy。一次读取该用户全部 ACTIVE 知识标签后，让 LLM 判断：

```text
该学习内容是否属于某个已有知识标签？
```

判断的是父子归属关系，而不是同义关系。

例如：

```text
Java线程池 属于 Java
Java网络编程 属于 Java
JVM垃圾回收 属于 Java
```

只有该用户不存在合理父标签时，才允许创建新的知识标签。不同用户可保留不同但合理的名字，例如一个用户使用“网络编程”、另一个用户使用“Web 编程”；核心职能才使用全局标准桶。

## 9. 第三阶段：职能能力判断

### 9.1 职能更新门槛

以下活动默认只更新知识标签：

- 观看视频；
- 阅读文章；
- 阅读文档；
- 完成低难度选择题；
- 听讲座；
- 浏览课程；
- 单纯记忆知识。

以下活动可以更新职能能力：

- 实际编程练习；
- 综合实验；
- 微项目；
- 企业项目；
- 案例分析；
- 设计任务；
- 完整报告；
- 仿真任务；
- 实操考试；
- 导师验收；
- 真实业务产出。

规则：

> 职能能力表示“能够完成工作”，不能仅凭接触过相关知识更新。

### 9.2 职能候选召回

根据学习证据文本，从 372 个标准职能桶中召回 Top 8～12。当前实现以桶名、别名、职能说明和证据标题/描述/复盘/事实点做本地确定性排序，并在审计中保留命中短语和召回置信度；后续语料和规模增长后可替换为 embedding / 混合召回，不改变候选输入输出契约。

LLM 只能从候选中选择，允许选择：

- 0 个；
- 1 个主职能；
- 最多 2 个辅助职能；
- 极少数综合项目最多 3 个。

禁止一次活动更新大量职能。

### 9.3 职能分类输出

```json
{
  "eligible_for_function_update": true,
  "function_updates": [
    {
      "bucket_id": "backend-development-id",
      "bucket_name": "后端开发",
      "role": "PRIMARY",
      "confidence": 0.94,
      "reason": "用户实现了完整的服务端库存业务逻辑，并处理并发和回滚问题"
    },
    {
      "bucket_id": "distributed-system-id",
      "bucket_name": "分布式系统开发",
      "role": "SECONDARY",
      "confidence": 0.76,
      "reason": "项目包含异步消息和分布式状态一致性处理"
    }
  ]
}
```

无法找到合理候选或仅有学习接触、没有真实交付时：

```json
{
  "eligible_for_function_update": false,
  "function_updates": [],
  "status": "REVIEW_REQUIRED",
  "reason": "现有证据不足以证明用户已能承担某项标准职能"
}
```

第一版本不要自动创建新职能桶。

## 10. LLM 提示词要求

建议拆成两个 Prompt，不要让一个 Prompt 同时完成全部任务。

### 10.1 知识归类 Prompt

```text
你是个人长期知识能力归类器。

你的任务不是创建尽可能多的标签，而是把学习活动归入稳定、粗粒度、可长期积累的知识与技术标签。

判断依据是上下位归属关系，而不是词语相似度。

例如：
- Java线程池、Java并发、JVM、Java网络编程，都可以归入“Java”。
- D触发器、组合逻辑、时序逻辑，可以归入“数字电路”。
- 日语听力、敬语、语法，可以归入“日语”。

优先使用已有标签。
只有不存在合理父标签时，才允许创建新标签。

禁止创建：
- 单个知识点；
- 单节课程；
- 单个项目；
- 过细的机制；
- 带有“入门、进阶、第一章”等课程式名称的标签。

输出严格JSON。
```

### 10.2 职能归类 Prompt

```text
你是职业职能能力分类器。

你的任务是判断一次学习证据是否能够证明用户具备某种工作职能。

职能表示“能够完成某类工作”，而不是“接触过相关知识”。

只有包含实践、项目、设计、分析、实操、交付物或有效测评的证据，才能更新职能能力。

单纯观看视频、阅读文章、学习理论或完成简单选择题时：
eligible_for_function_update 必须为 false。

你只能从提供的标准职能候选中选择。
不要创建新的职能名称。
最多选择一个主职能和两个辅助职能。
没有合适职能时返回空数组。

输出严格JSON。
```

## 11. 分数计算

能力更新不要完全依赖 LLM 直接给分。

LLM 负责：

- 分类；
- 判断主次；
- 输出置信度；
- 提取细知识点。

后端规则负责计算分数。

推荐公式：

```text
score_delta
= base_weight
× difficulty_factor
× performance_factor
× confidence
× role_factor
```

建议基础权重：

```text
VIDEO / READING           1
QUIZ                      2
EXERCISE                  3
PRACTICAL_LAB             4
MICRO_PROJECT             6
ENTERPRISE_PROJECT       10
MENTOR_REVIEW             8
```

职能能力只对允许更新职能的证据计算分数。

主次职能系数：

```text
PRIMARY     1.0
SECONDARY   0.5
```

难度系数示例：

```text
1级  0.8
2级  1.0
3级  1.2
4级  1.5
5级  1.8
```

表现系数建议限制在：

```text
0.6 ～ 1.2
```

置信度低于某个阈值时不自动更新：

```text
confidence < 0.65
→ REVIEW_REQUIRED
```

具体阈值放进配置，不要写死在业务逻辑中。

  "SILVER": 100,

## 14. 旧数据迁移

必须采用非破坏式迁移。

### 14.1 迁移原则

旧标签不直接删除。

先建立新表，然后将旧标签映射为：

- 知识标签；
- 职能标签；
- 细知识点；
- 无法确定，进入审核队列。

示例：

```text
Java基础       → 知识标签 Java，细知识点 Java基础
Java高并发     → 知识标签 Java，细知识点 并发编程
Java网络编程   → 知识标签 Java，细知识点 网络编程
后端开发       → 职能标签 后端开发
Redis          → 知识标签 缓存技术，细知识点 Redis
```

### 14.2 分数迁移

如果旧系统保存了证据级数据，应根据证据重新计算。

如果只有旧标签总分，不建议简单全部相加，否则会造成能力膨胀。

建议迁移公式：

```text
新桶分数
= 最高旧标签分数
+ 其他旧标签分数之和 × 0.3
```

例如：

```text
Java基础      100
Java并发       80
Java网络编程   60
```

迁移后：

```text
Java = 100 + (80 + 60) × 0.3 = 142
```

同时保留原始标签作为细知识点。

### 14.3 双写阶段

建议短期保留：

```text
旧能力系统写入
新能力系统写入
```

运行一段时间确认结果稳定后：

1. 前端切换到新系统；
2. 停止旧系统写入；
3. 旧表进入只读状态；
4. 最后再决定是否清理。

## 18. 验收标准

本需求完成后，应满足以下条件：

1. 个人能力页面明确分为“核心职能”和“知识与技术”；
2. `Java高并发、Java网络编程、Java基础` 不会继续作为三个并列一级标签；
3. 上述内容能够归入 `Java` 并保存为细知识点；
4. 单纯学习 Java 课程不会自动获得“后端开发”能力；
5. 完成真实后端项目后，可以更新“后端开发”；
6. 数字电路可以作为知识标签存在，不必提前判断用于汽车还是船舶；
7. 职能标签只能来自标准职能桶；
8. 每次能力增长都可以追溯到具体学习证据；
9. 同一证据不会重复加分；
10. 当前学习路径图谱不受本次改造影响；
11. 页面不增加行业标签；
12. 低置信度和无法匹配的结果能够进入审核流程；
13. LLM 输出失败不会导致学习活动主流程失败；
14. 新系统能够兼容并迁移旧能力标签数据。
