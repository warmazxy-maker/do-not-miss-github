## 二、事务边界

> 深入讲解（含比喻、代码和问答纠错）见 [学习笔记_事务边界与Spring代理.md](学习笔记_事务边界与Spring代理.md)。

1. **只读事务里的写入会失败**：`recommendEvents` 标了 `readOnly = true`，记录曝光的方法如果加入这个事务，写入就会失败。做法是给 `recordImpressions` 加上 `REQUIRES_NEW`，让它自己开一个可写的事务。**原理**：传播行为决定了被调用的方法是加入调用方的事务，还是自己另开一个。
2. **统计代码不能拖垮主业务**：预约服务只发布领域事件；监听器用 `AFTER_COMMIT`，等预约提交成功后才执行，并且在新事务里运行、出错只记日志。**原理**：主业务必须可靠，统计尽力而为。能接受的状态是“主业务成功、反馈缺失”，不能接受的是“反馈说预约了但其实没有”，或者“因为反馈失败导致预约失败”。
3. **幂等**：
   - 删除时，要删的东西本来就不存在，返回的 404 算成功；
   - 去重靠数据库唯一约束 `(impression_id, feedback_type)`，不靠“先查再插”。
   - **原理**：消息会重复投递、操作会重试，每个操作都要回答“执行两次会不会出错”。

## 三、可观测性

| 做法 | 原理 |
|---|---|
| 每个依赖独立探活，一个挂了只影响自己那张卡片 | 监控本身不能因为被监控的东西坏了而跟着失效 |
| 用载荷里的 `recordId` 和运行记录开头的 `sessionId=` 把没有外键的表串成链路 | 分布式追踪里 traceId 的雏形 |
| 一次失败后又重试了，就标成“已重试”，不算当前失败 | 告警看最新状态，不看历史事件 |
| “闲置队列”和“单节点 yellow”不算降级 | 告警按“有没有人受影响”来设计，否则面板一直红着就没人看 |
| 未知异常必须写日志 | 用户只看到“服务器内部错误”，原因要是不进日志，就永远丢了 |


### 大白话版（2026-10-24 补充）

**可观测性是什么**：好比开车。你不会把发动机拆开看，靠的是仪表盘（指标）、故障灯（告警）和行车记录仪（日志、追踪）。可观测性就是不用拆开系统，也能从外面回答两个问题：“系统现在好不好？不好的话，问题出在哪、为什么？”业界说的三根支柱，在我们项目里分别是：日志对应后端日志，指标对应总览卡片、零结果率和 P95 耗时，追踪对应 Agent trace 和链路追踪。

1. **一个探头坏了，不能让整块仪表盘黑掉**：烟雾报警器要有自己的电池。每个依赖单独检查，出错就显示一张红色卡片，其他卡片照常显示。监控系统要比被监控的系统更皮实。
2. **没有外键，就用“快递单号”串起来**：快递经过不同公司、不同系统，靠同一个单号串成完整轨迹。我们用的“单号”是消息里的 `recordId`，以及 Agent 运行记录开头的 `recordId=` / `sessionId=` / `resumeEvidenceId=`。成熟的做法是 traceId（OpenTelemetry）。代价是这是一种隐式约定，有人改了格式就会悄悄断链。
3. **看最新状态，不看历史事件**：快递显示“第一次派送失败 → 第二次派送成功”，你不会说快递失败了。失败之后又重试过的，标成“已重试”，不计入结论；历史保留，用来查原因。
4. **告警只报真正影响到人的问题**：炒个菜就响的烟雾报警器，最后会被拔掉电池（狼来了）。闲置的死队列、单节点 OpenSearch 的 yellow 都不算降级；只有“有消息在等却没人消费”或“消费者停了”才算。设计告警时问的是“这个状态会不会让某个人受影响”。
5. **报错一定要留下记录**：黑匣子是空的，事故原因就永远查不清。兜底异常处理器原来返回 500 却不写日志，现在会记录完整的错误堆栈；请求格式不对属于用户的错，改成返回 400。
6. **看得见，也要守得住**：Redis 的登录会话键只统计数量，从不显示键名。监控页面本身也可能成为泄露数据的口子。

> 一句话：仪表盘要比车皮实；用单号串起整条链路；看现在，不看过去；只为真问题报警；任何报错都要留下记录。
>

## 四、数据建模：推荐系统的基本功

- **曝光是分母**：感兴趣率 = 感兴趣次数 ÷ 推荐出去的次数。没有曝光记录，就算不出任何比率。
- **反馈挂在曝光上**，而不是挂在“学生 + 活动”上：这样才知道是哪一次推荐、排第几、什么需求带来了这个反馈。
- **按推荐当天统计（cohort）**：周一推荐、周三才预约，这次预约算在周一。这样每天的数字反映的是那天推荐的质量。
- **最后触点归因**：预约算到 7 天内最近一次推荐头上。简单、好解释，局限是会把功劳全算给最后一次推荐。


### 大白话版：试吃摊（2026-10-25 补充）

1. **曝光是分母**：只知道“30 人买了”判断不了试吃好不好，得先知道“发出去多少份”。一次推荐展示 5 个活动，就算 5 次曝光。零结果的推荐没有曝光记录，所以零结果率要从运行记录里读。
2. **反馈挂在“那一次曝光”上**：顾客路过三次才买，要知道是哪一次、什么口味、摆在第几排起了作用。这样才能比较名次的影响、新旧算法的好坏。
3. **按推荐当天统计（cohort）**：周一发的试吃，周三才回来买，算周一的功劳。否则只发了 2 份试吃的周三，会显示出 750% 这种离谱的转化率。
4. **最后触点归因**：三次试吃才买，功劳算给 7 天内最近那次。好处是简单好解释，缺点是前几次的贡献被忽略了。

## 五、评测工程

1. **可复现第一**：评测原来依赖了活动数据、搜索索引、当前时间和运行者的画像。现在全部固定下来：冻结语料、专用索引、固定时钟 `asOf`、中性画像。
2. **依赖倒置**：`EventCorpus` 接口有线上和冻结两个实现，召回和打分代码只有一份。评测测的必须是线上真正在跑的代码。
3. **内容寻址**：评测索引名带上“语料文件 + 向量模型”的 SHA-256 指纹，内容一变名字就变，旧索引自然不会再被用到。Git 和 Docker 用的是同样的思路。
4. **评测集像数据库迁移一样走版本管理**：运行中的系统只生成下一版的预览，由人审核、提交到 git 才生效。
5. **一个指标只回答一个问题**：“该出现的出现了吗”看 NDCG / MRR；“不该出现的出现了吗”看拒绝命中率。两类指标分开统计。


### 大白话版：考试（2026-10-25 补充）

1. **可复现，就是同一张卷子、同一个考场**：活动过期等于题目对应的课本被收走了，所以冻结语料；真实时间等于每次考试难度不同，所以固定时钟；带着个人画像等于带小抄，所以用中性画像。
2. **依赖倒置，就是考场和马路开的是同一辆车**：如果另写一套召回专门用来评测，考过了也说明不了线上那套好不好。`EventCorpus` 接口负责切换“路”（线上或冻结数据），召回和打分这辆“车”只有一份。
3. **内容寻址，就是卷子上印防伪码**：索引名带上“冻结文件内容 + 向量模型”的指纹，内容一变名字就变，不会拿旧向量去评新语料。
4. **版本化，就是题库换版要审核、要编号**：系统只生成下一版草稿，人审核后提交，和 Flyway 是同一个思路，不能在考试中途偷偷换题。
5. **一个指标只回答一个问题**：选择题（NDCG、MRR）和判断题（拒绝命中率）分开算分。只有“不该出现”标记、没有正确答案的题，不能拿去算 NDCG，否则会白白拉低平均分。

#### 追问：“名字叫活动 A，内容改了，引用不就读到最新的了吗？”（2026-10-25）

- **按 ID 读数据库时确实如此**：`find(27)` 每次都读到最新的那一行。
- **但搜索索引不是引用，而是提前加工好的副本**，就像书后面的索引页。正文改了，索引页不会自己变，除非重新印。建索引时，活动会被加工成分词文本和向量（由向量模型算出来的一串数），然后单独存起来。这么做是因为不能每次搜索都把全部原文重新分词、重新算一遍向量。
- **活动 27 的例子**：活动 27 原来是“Java 零基础入门”，建好了索引。之后有人把文件改成“Go 语言入门”，但索引名没变，系统以为索引还能用，就不重建。结果搜“Java 入门”时，靠旧索引命中了 27；用 `find(27)` 取详情，拿到的却是新内容“Go”。搜“Go”反而搜不到它。整个过程不报任何错，只是分数悄悄错了。
- **换向量模型更严重**：不同模型的向量就像不同的坐标系，v5 的查询向量和 v4 的文档向量放在一起算相似度，结果毫无意义。
- **指纹的作用**：用很低的成本判断“到底变没变”。指纹 = SHA-256（文件内容 + 模型名），写进索引名。没变就复用，不花钱；变了，名字就变，系统找不到同名索引，就会重建。这叫**内容寻址**（名字由内容决定，适合做缓存），区别于**按名字寻址**（名字固定，内容可变，适合“我要最新的”）。
- **线上索引怎么跟上**：活动一有变化，就发一条 `event.index` 消息，监听器只更新那一个活动（改了就主动通知）。评测索引则靠指纹发现变化后整个重建。两者的共同点是：副本必须有一个机制跟上原始数据，否则就会悄悄过期。

## 六、LLM 系统的设计原则

- **语义判断交给模型，Java 只守结构**。关键词守卫的教训：测试时随口说的“大阪”“最好”被写成了规则，结果把完整的需求也拦了下来。
- **没有模型时原样透传数据，不做推断**：B3 没有模型时只列出原始反馈，不尝试归纳。
- **用户原文只当数据，不当指令**：用来防提示注入。
- **长期记忆不能压过当下意图**：避免推荐越来越窄（过滤气泡）。
- **用户明确的选择，用结构性规则直接执行；语义上的推断，交给模型判断**：“这个活动不要”可以用 Java 直接过滤；“类似的也不要”交给模型。

## 七、测试方法

- 测试抓到过我自己的 bug：
  - 合并上下文时，把用户第一句的条件弄丢了；
  - 引导 Agent 的 `sessionId=7cee…`（一个 UUID）被误读成了会话 7。
- **把计算逻辑抽成纯函数**：漏斗、按天统计、导出评测集都不依赖数据库，测起来快而且稳定。
- **把不变量写成测试**：比如“所有标注的活动都在语料里”“评测时钟早于每个冻结活动的结束时间”。
- **往返测试**：导出的文件必须能被真实的读取代码重新读进来。

## 八、安全

- 运维接口拒绝访问时返回 404，不暴露接口的存在。
- `/reindex` 原先完全没有鉴权，已补上。
- 不能伪造隐式反馈（返回 400），也不能评价没推荐给自己的活动（返回 404）。
- 评测用例要提交到公开仓库，所以导出时去掉 userId，并要求审核人删除需求原文里的个人信息。
