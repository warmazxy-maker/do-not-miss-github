## 二、你在现状摸底上的追问

### “为什么推荐 4 次、引导对话 6 次？”

你说行动计划是多 Agent，这个懂，但另外两个为什么也这么多。我拆开讲：
- 推荐是一条四步流水线：改写需求、向量化、排序、质检；
- 引导对话先判断你想干嘛，要推荐就把整条推荐流水线跑一遍，对话太长了还要压缩一次。

### “占线程就是怕点多了别人的资源被耗尽？”

对。这个问题直接引出了后面的“并发闸”。

### “能力起名到底是哪一种？”

我一开始把两套系统混在一起讲了：先说“现在是先起名后查”，又说“V2 已经是你说的第二种”。你追问：

> 到底是哪一种啊，咱们现在用的就是 V2。

我澄清：V2（在用的）已经是“把已有标签给模型，能复用就复用”；有漏洞的是旧版能力聚类，前端已经不调了。

然后你追问“没变就不问”：

> 记住不还是得靠模型吗？要用 Java 硬规则记？那还不如不省这个钱，之前 GPT 写一大堆 Java 规则没把握坑死。

你用一个例子把问题讲透了：先参加程序开发活动，记下“Java 后端、MySQL”；之后参加 Java 程序设计大赛，模型再看一眼，复用“Java”。**第二次就应该调模型，因为这是一份新证据**。我确认“没变就不问”只适用于“同一份输入被反复问”，V2 不加任何这类东西。

最后你的决定：

> 旧版的不都不用了吗，还管它干嘛。

**你的思考**：你对“用 Java 规则替代模型判断”非常警惕，这和之前的经验一致（见记忆里的“不要用关键词规则覆盖模型判断”）。另外你看重的是**投入值不值**：一个没人用的旧页面，不值得为它加任何逻辑。

### 关于第 2 题的一处确认

你说“按照 IP + 账号”。我解释：登录后的 AI 接口**只按账号**更合适，因为按“IP + 账号”的话，换个网络就是一个新计数器，额度会翻倍；“IP + 账号”用在登录上。这是在你的原意上做的细化。

### 关于并发闸的理解校准

你的理解是“虽然允许一分钟三次，但最好别一秒就用完”。我校准了一下：那是令牌桶的感觉；并发闸只管“同时有几个还没跑完”，一秒内发两次没问题，两个都还在等模型时再发第三个才会被挡。

## 四、从这些回答里提炼出的你的设计原则

1. **先懂原理再做决定**：算法和并发闸都先要求讲透，再拍板。
2. **不用 Java 规则替代模型的判断**：宁可多花一次调用，也不写“没把握”的规则。
3. **不为没人用的东西投入**：旧版能力聚类直接不管。
4. **先能看见，再谈控制**：总预算先只显示，不做自动暂停。
5. **能复用就复用**：接口分档“只是多个标签”，和 D1 的权限注解同一个路子。

## 五、我在实现中补的决定

| 决定 | 原因 |
|---|---|
| “提交活动审核”放在状态机入口计数，不标在接口上 | 只保存草稿不该算；只有真正送去 AI 的那一步才花钱 |
| 一分钟内被拒绝的请求不扣当天额度 | 先查短窗口，否则狂点一分钟就把一天的额度用完了 |
| “一天”按东京时间算 | 与项目里其他按天统计的地方一致 |
| 并发闸的名额 5 分钟后自动过期 | 行动计划会连续调用好几次模型，60 秒不够 |
| 重 AI 和普通 AI 共用一个并发闸 | 闸防的是线程被占满，不分功能 |
| 账号不存在也算一次输错 | 否则从回复里能判断账号是否存在 |
| 第 5 次输错直接返回“已锁定” | 让用户立刻知道，不用再试一次才发现 |
| 开启 `forward-headers-strategy=native` | 部署在 nginx 后面时，否则所有人共用 nginx 的 IP（PROBLEM_LOG 072） |
| 模型调用计数在模型客户端里做 | 所有调用都经过它，不会漏，也不用改各个业务代码 |
| 前端不改请求代码 | 原有的错误提示会直接显示后端写好的“请 X 秒后再试” |
