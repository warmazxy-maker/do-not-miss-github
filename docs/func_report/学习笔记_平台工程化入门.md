# 学习笔记：平台工程化是什么（方向 D 开篇）

> 2026-10-25，开始方向 D 之前的大白话介绍。具体实现见之后的 D 阶段报告。

## 一句话

**平台工程化，就是把“能跑起来的原型”，升级成“能放心交给很多人长期使用的平台”。**

业务功能（推荐、能力标签、简历定段）回答的是“系统能帮学生做什么”。平台工程化回答的是：**谁能做什么？流程怎么走才不会乱？被滥用了怎么办？**

## 比喻：从小吃摊到连锁餐厅

小吃摊什么都在老板脑子里。开成连锁餐厅就必须有：
- **规章流程**：一道菜从下单到上桌，每一步谁负责、下一步是什么，都写成固定流程。对应**状态机**。
- **门禁和工牌**：服务员进不了财务室。对应**权限（RBAC）**。
- **排队取号**：客人太多时先排队，不能把厨房冲垮。对应**限流**。
- **监控和账本**：出了问题能查。对应已经做过的 Outbox、运维面板、Agent trace。

## D 的三件事

### 1. 审核状态机：规章流程
- 活动的状态：草稿 → 待审核 → 通过 / 需要修改 → 重新提交 → 已过期 / 被下架。
- **现状的问题**：审核状态和“是否过期”是两个分开的字段，质量分析、过期任务、删除操作各自直接去改，没有统一的“哪些状态之间可以变化”的规则；被打回的活动没有重新提交的路，也没有运营后台来处理。
- **状态机**：明确规定有哪些状态、哪些状态之间可以变化、谁能触发、变化时顺带做什么。不在表里的变化，一律拒绝。就像网购订单不可能从“待付款”直接跳到“已签收”。
- **项目里已有的范例**：简历定段会话状态里的 `canMoveTo`。

### 2. 权限（RBAC）：工牌
- **现状**：用户角色只有学生和社会组织两种；运维面板靠环境变量白名单控制（`OPS_ADMIN_USERS`）；`/reindex` 曾经完全没有鉴权。
- **白名单的问题**：改名单要改配置、重启服务；一个人到底能做哪些事，要翻好几个地方才知道；谁什么时候被加进来的，没有记录。
- **RBAC**：先定义权限，再把权限打包成角色，最后给用户分配角色。门禁只认工牌的类型，不认名单。

### 3. 限流：排队取号
- **为什么需要**：很多接口背后要调用大模型，每次调用都花钱、都要等十几秒。有人用脚本刷接口，账单会爆，正常用户的请求也排不上。
- **限流**：给每个人或每个接口设一个速度上限，超出的请求直接拒绝。就像地铁早高峰在站外限流，控制的是进来的速度。
- **常见算法**：
  - **固定窗口**：最简单，但在两个窗口交界处可能短时间放进两倍的量；
  - **滑动窗口**：统计“过去 60 秒”内的请求数，更平滑；
  - **令牌桶**：按固定速度往桶里加令牌，每个请求拿走一个，允许短时间突发，同时控制平均速度。
- 计数要放在 **Redis** 里，因为将来可能部署多台后端，计数必须是共享的。

## 为什么现在做

- 花模型调用的功能越来越多，被滥用的代价越来越大；
- 管理员操作（运维面板、审核候选、重建索引）越来越多，靠白名单管不过来了；
- 活动有好几种状态，却没有统一的规则，迟早会出现“不应该出现的状态”。

> 这三件事单独看都不是新功能，但它们决定了这个系统能不能放心交给很多人用。
