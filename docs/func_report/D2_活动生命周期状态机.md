## 一、用大白话说，这次做了什么

以前，一个活动“现在是什么情况”记在两个字段里：`review_status`（审核状态）和 `expired`（是否过期）。有 5 个地方各自直接改这两个字段：发布、AI 审核、人工通过、人工驳回，以及定时任务。**这就像一个仓库有 5 扇门，每扇门都能直接搬货，却没人登记**。结果是：

- 谁都可以把活动改成任何状态，没有地方检查“现在能不能这样改”；
- 改完之后要做的事（更新搜索索引、触发 AI 审核）每个地方各写一遍，漏写了就出 bug；
- 出了问题，查不到这个活动经历过什么。

D2 把 5 扇门换成**一扇门加一个门卫**：

- **一扇门**：所有状态变化都只能调用 `EventLifecycleService.transition(活动, 动作, 谁, 原因)`；
- **门卫手里有一张表**：哪个状态下、谁、做什么动作、会变成什么状态（`EventLifecycleRules`）；
- **门口有登记簿**：每次变化写一条状态历史；
- **进出门时自动做的事**：进入“已上架”就写入搜索索引，离开“已上架”就从索引删除；进入“审核中”就通知 AI 来审。

## 二、它在系统里的位置

```
组织端 ──┐
运营端 ──┤                     ┌─ 转移表 + 守卫（纯函数，EventLifecycleRules）
AI 审核 ─┼─> transition(...) ──┼─ 改状态和相关字段（下架原因、修改意见、审核路线）
定时任务 ┘                     ├─ 副作用：索引 UPSERT/DELETE、AI 审核消息（都走 Outbox）
                               └─ 写一条 event_status_history
学生端 ──> 只读：搜索、召回、预约，看到的是后端算好的“学生视角状态”
```

这是**写链路的收口**。读链路（搜索、召回）不再写任何东西。

## 三、关键决策

### 决策 1：两个维度分开，时间维度不存

| | 发布维度 | 时间维度 |
|---|---|---|
| 取值 | 已保存、审核中、需修改、已上架、已下架 | 未开始、进行中、已结束 |
| 谁来改 | 只有状态机 | 时钟（没人改，自己走） |
| 存不存 | 存在 `review_status` | **不存**，每次按开始、结束时间计算 |

**问题**：原来的 `expired` 字段需要有人去“刷新”：定时任务五分钟刷一次，嫌慢，又在每次搜索前刷一次。

**选择**：能算出来的东西就不存。`EventEntity.hasEnded(now)` 和 `EventTimePhase.of(event, now)` 每次现算。

**好处**：没有“刷新不及时”的问题，也没有“读的时候顺手写”的副作用；评测时传入固定时钟 `asOf`，就能复现当时的结果。

**代价**：每个查询都要带上时间条件（`end_time > now`），并为此新建了索引 `(review_status, end_time)`。

**“回调”是什么**：你说“时间维度到了已结束，通过一个回调让发布维度变成已下架”。这个回调就是 `EventExpirationService`：它找出“已上架但已经结束”的活动，调用状态机执行 `END`，把它们转成“已下架（活动已结束）”。**学生能不能看到一个活动并不依赖它**，它只负责整理发布状态，晚几分钟也没关系。

### 决策 2：一张纯函数的转移表

```java
TABLE.put(SUBMIT,       new Rule(Set.of(DRAFT, NEEDS_REVISION, OFFLINE), PENDING_REVIEW, Set.of(ORGANIZER), false, true));
TABLE.put(TAKE_OFFLINE, new Rule(Set.of(APPROVED), OFFLINE, Set.of(ORGANIZER, OPERATOR), true, false));
TABLE.put(RELIST,       new Rule(Set.of(OFFLINE), APPROVED, Set.of(OPERATOR), false, true));
```

每一行读作：“这个**动作**，可以从这些**状态**出发，变成这个**状态**，允许这些**人**做，是否必须写**原因**，是否要求活动**还没结束**。”

| 动作 | 从 | 到 | 谁 |
|---|---|---|---|
| SUBMIT 提交 | 已保存、需修改、已下架 | 审核中 | 组织 |
| REVISE_PUBLISHED 修改已上架的活动 | 已上架 | 审核中 | 组织 |
| REANALYZE 重新分析 | 审核中、需修改 | 审核中 | 组织、运营 |
| AI_APPROVE / AI_REQUEST_REVISION | 审核中 | 已上架 / 需修改 | AI |
| MANUAL_APPROVE 人工通过 | 审核中、需修改 | 已上架 | 运营 |
| MANUAL_REQUEST_REVISION 人工要求修改（需原因） | 审核中 | 需修改 | 运营 |
| TAKE_OFFLINE 下架（需原因） | 已上架 | 已下架 | 组织（自己的）、运营 |
| END 结束 | 已上架 | 已下架（ENDED） | 系统 |
| RELIST 重新上架 | 已下架 | 已上架 | 运营 |
| DISCARD 放弃 | 已保存、需修改 | 已下架（DISCARDED） | 组织 |

**为什么写成纯函数**：这张表不碰数据库、不发消息，所以整个状态机可以用普通单测覆盖，也可以一眼读完。**规则（能不能）和副作用（变了之后做什么）分开**，是这次最重要的结构。

**守卫返回不同的错误码**：动作和当前状态不匹配返回 409（冲突）；人不对返回 403；没写原因或活动已结束返回 400。前端据此给出不同的提示。

### 决策 3：副作用绑定在“进入或离开某个状态”上，而不是绑定在“某个动作”上

```java
if (from == APPROVED && to != APPROVED) → 索引 DELETE
if (to == APPROVED && !ended)          → 索引 UPSERT
if (to == PENDING_REVIEW && route == AI) → 发 AI 审核消息
```

**为什么**：能离开“已上架”的动作有好几个（下架、结束、修改后重审）。如果按动作写，就要写三遍“删除索引”，以后加第四个动作时很容易漏掉。按状态写，**以后不管加什么动作，只要离开了“已上架”，索引一定会被删掉**。

所有消息都通过 Outbox 发出（B 阶段学过）：和状态变化在同一个事务里写入，**状态改成功了消息才会发，状态没改成功消息也不会发**。

### 决策 4：AI 直接决定，但三次之后转人工

- AI 建议 APPROVE → 已上架；建议 NEEDS_REVISION 或 REJECT → **都变成需修改**，并把缺失信息和风险标记写成修改意见给组织看。
- 每次 AI 要求修改，`ai_revision_count + 1`。达到 3 次后，下一次提交时 `review_route = MANUAL`，**不再发 AI 消息**，等运营处理。
- 任何一次通过都会把计数清零，路线重置为 AI。

**为什么“走哪条路”在进入审核中时决定**：路线是这一次提交的属性，进入审核中的那一刻就定下来，之后不会再变。

### 决策 5：AI 消息要幂等

AI 审核是异步的（MQ 消息）。消息可能重复投递，也可能在这期间运营已经人工处理过了。所以 `analyzeById` 一开始就检查：**活动还是“审核中”并且路线是 AI 吗？不是就直接跳过**，既不调用模型（省钱），也不会覆盖人工的决定。就算检查漏掉了，状态机本身也会拒绝（AI_APPROVE 要求当前状态是审核中，否则返回 409）。这叫**双保险**。

### 决策 6：乐观锁

`EventEntity` 加了 `@Version`。Hibernate 每次更新都会执行 `UPDATE events SET ..., version = version + 1 WHERE id = ? AND version = ?`。如果两个运营同时处理同一个活动，后提交的那个会更新到 0 行，Hibernate 抛出 `ObjectOptimisticLockingFailureException`，`GlobalExceptionHandler` 把它转成 **409“数据已被其他人修改，请刷新后重试”**。

**为什么不用悲观锁（`SELECT ... FOR UPDATE`）**：同一个活动被同时处理的情况很少见。悲观锁每次都要加锁、等锁；乐观锁平时没有任何成本，只在真的冲突时才报错。

### 决策 7：不同的人看到不同的说法（投影）

同一个活动，后端给两种视图：

- **组织视图** `OrganizerEventResponse`：发布状态、修改意见、下架原因、审核路线，以及**现在能做哪些操作**（`canEdit`、`canSubmit`、`canTakeOffline`……）。前端只看这些布尔值来决定显示哪些按钮，**不在前端重新实现一遍状态机**。
- **学生视图** `EventStudentView`：只有一个状态。已上架就显示时间状态；已结束就显示“已结束”；被下架就显示“已下架：原因”；重新审核中就显示“已下架：活动重新上架审核中”。**修改意见是组织和平台之间的事，学生看不到**。

这回应了你在 L1 里说的“前端两条线挺乱”：组合两个维度的工作全部放在后端。

### 决策 8：软删除

`DELETE /api/events/{id}` 现在的含义是“放弃”：只能放弃从没上架过的活动（已保存、需修改），活动变成“已下架（DISCARDED）”，**数据库里一行都不删**。已上架的活动只能“下架”，并且要写原因。外键报错的问题自然就消失了。

### 决策 9：预约守卫和签到

- **预约**：只有已上架并且没结束的活动可以预约。
- **下架或结束不取消预约**：预约列表里每条预约都带一个 `notice`，例如“活动已结束，请处理”“活动已下架：场地调整”，前端用红色醒目显示。重新上架后提示自动消失（它是每次现算的）。
- **签到**：删掉学生自助签到的 `/api/reservations/scan-complete`，新增 `POST /api/events/{id}/check-in`，只有活动的发布者能用。组织在“我的事件”里点“签到”，输入或扫描学生凭证上的 token。

## 四、一次请求的完整路径：组织修改一个已上架的活动

1. 前端 `PUT /api/events/12`，带着修改后的内容。
2. `PermissionAspect` 检查当前用户有没有 `EVENT_PUBLISH` 权限（D1），并记审计日志。
3. `EventService.update`：
   - 是不是自己的活动？不是就返回 403；
   - 是“审核中”吗？是就返回 409（审核中的内容不能改）；
   - 写入新字段，再检查一次组织归属；
   - 原来是“已上架”，所以调用 `transition(REVISE_PUBLISHED)`。
4. `EventLifecycleRules.check`：已上架 → 审核中，组织、自己的活动、活动未结束，检查通过。
5. `EventLifecycleService`：
   - 决定审核路线：计数小于 3，走 AI；
   - 改状态，`save` 时 `version` 加 1；
   - 副作用：离开“已上架”，写一条“删除索引”的 Outbox；进入“审核中”并且走 AI，写一条“AI 审核”的 Outbox；
   - 写一条状态历史：`APPROVED → PENDING_REVIEW, REVISE_PUBLISHED, ORGANIZER`。
6. 事务提交。Outbox 投递器把两条消息发到 RabbitMQ。
7. 索引消费者删掉索引，学生搜不到了。已预约的学生在“我的预约”里看到“活动已下架：活动重新上架审核中”。
8. AI 消费者收到消息，检查活动仍在等待 AI 审核，调用模型，然后 `transition(AI_APPROVE)`。进入“已上架”，写一条“写入索引”的 Outbox，学生又能搜到了，预约里的提示也消失了。

## 六、已知边界与后续

- **运营的操作界面还没有**：人工审核队列、重新上架按钮、人工要求修改的输入框，这些都是 D3 的内容。接口已经有了（`/review/approve`、`/review/reject`（需原因）、`/relist`、`/offline`），但目前没有页面能点。**三次之后转人工的活动，在 D3 之前只能通过调接口处理**。
- **组织冒充的缺口仍然存在**（D1 的 `AUTO_JOINED`）。
- **签到只支持输入 token**，没有接摄像头扫码。
- 编辑页面靠 `mine()` 列表找活动，没有单独的“获取单个活动”接口。
- `REJECTED` 留在枚举里，目前没有任何代码会产生它。
- V33 会把已有数据里“已通过并且已过期”的活动转成“已下架（活动已结束）”，把“已拒绝”的活动转成“需修改”。都是测试数据，影响不大。

## 七、可迁移的模式

1. **状态机 = 转移表 + 守卫 + 副作用 + 历史**。表和守卫写成纯函数，副作用放在服务里。订单、工单、审批流都可以这样做。
2. **能算出来的就不存**：存一个派生值，就要负责一直同步它。
3. **副作用绑定在状态上，而不是动作上**：加新动作时不会漏掉。
4. **一个入口**：所有修改都走一个方法，规则和日志才能集中。
5. **异步消费者先检查“这件事还该我做吗”**：这样就做到了幂等。
6. **投影**：同一份数据，按观看者给出不同的视图，前端不重复实现业务规则。
7. **软删除**：业务数据用状态表达“没了”，引用关系永远完整。

### 面试怎么讲（STAR）

- **S**：活动状态分散在两个字段里，有 5 处各自直接修改。删除有人预约过的活动会撞外键；预约不检查活动状态；每次搜索都会顺手写数据库；学生可以自己给自己签到。
- **T**：把活动生命周期做成可以验证、可以追溯的状态机，同时不能破坏推荐评测（评测依赖固定时钟）。
- **A**：把“发布”和“时间”拆成两个维度，时间维度不存储，按时间计算；所有状态变化走同一个入口，转移表写成纯函数；副作用绑定在进入或离开状态上，并通过 Outbox 和状态变化放在同一个事务里；AI 消费者先做幂等检查；用 `@Version` 防止并发覆盖；删除改成软删除；签到改由组织完成；后端分别为组织和学生生成视图。
- **R**：状态变化从 5 处收口到 1 处，所有转移都可以用 22 个单测覆盖；读接口不再有写操作；外键报错和越权签到的问题消失；每个活动都有完整的状态历史。
