# 学习笔记：事务边界、领域事件与 Spring 代理

> 这份笔记来自 2026-10-24 的一次问答。我先讲解，你提出疑问，我再纠正。**纠正的部分特意保留了下来**，因为最容易想错的地方，正是最值得记住的地方。
>
> 涉及的项目代码：`AiService.recommendEvents`（只读事务）、`RecommendationFeedbackService.recordImpressions`（`REQUIRES_NEW`）、`ReservationService` / `FollowService`（发布领域事件）、`RecommendationActivityListener`（`AFTER_COMMIT` 监听器）。

---

## 1. 事务是什么

**比喻：银行转账。** A 给 B 转 100 元要做两步：A 的余额减 100，B 的余额加 100。如果做完第一步系统崩了，钱就凭空消失了。

**事务**就是把几步操作打成一个包：要么**全部成功（提交，commit）**，要么**全部当没发生（回滚，rollback）**，不存在“做了一半”的状态。

在 Spring 里，给方法加上 `@Transactional`，这个方法里的所有数据库操作就属于同一个事务：方法正常结束就提交，中途抛出异常就回滚。

**事务边界**：这个事务从哪里开始、到哪里结束、包含了哪些操作。本笔记讨论的所有问题，本质上都是在判断“某一步该不该放进这个事务里”。

## 2. 只读事务：既然只读，为什么还要写？

### 只读事务是什么
`@Transactional(readOnly = true)` 等于告诉 Spring 和数据库：“这段代码只查询，不修改。”这样做有两个好处：
- **性能**：Hibernate 不用跟踪查出来的对象有没有被改过，省掉了提交前检查改动这一步；数据库也可以做只读优化。
- **安全**：万一有人误写了修改语句，会被拦下来，或者不会生效。

### 我们遇到的情况
推荐方法 `recommendEvents` 本来只读：读画像、召回活动、模型排序，所以标了 `readOnly = true`，这个标记没有错。

B1 要在推荐结束时**顺手**记一笔曝光（推荐给谁展示了哪些活动），这是一次写入，结果被塞进了一个只读的方法里。

> 比喻：阅览室规定只能看书、不能写字。你看完书想在登记本上记一笔，就在阅览室里写，要么被管理员拦下，要么写了也不作数。

### 会发生什么（更正后的说法）
- **修改已经查出来的对象**：只读事务里，Hibernate 不会把改动同步到数据库，修改**悄悄丢失**。
- **插入新记录**（曝光属于这种）：我们的表用自增 ID，Hibernate 为了拿到 ID 会立刻执行 INSERT；而这个连接已经被设成只读，MySQL 会**直接报错**。
- 曝光记录外面包了 try/catch（原则是记录失败不能影响推荐），所以这个报错只会变成一行警告日志，推荐照常返回，**曝光表却一直是空的**。对使用者来说，效果就是“悄悄丢了”。

> 说明：这个坑是写代码时根据机制提前规避的，没有专门复现过。“报错还是静默丢失”是推理出来的结论。B1 报告里写的“不报错、悄悄丢失”不够准确，以这里为准。

## 3. 传播性：和“A、B、C 后面加了个 D”有什么关系

### 你最初的理解
> 原先 A、B、C 都是只读语句，包在只读事务里；后面又加了一个用来写的 D，所以出了问题。但这和事务的传播性有什么关系？

### 补上的关键细节
**D 不是直接写在后面的一行语句，而是去调用另一个类里的方法，而且那个方法自己也标了 `@Transactional`。**

**调用方**，就是发起调用的那个方法，这里是 `recommendEvents`。

```java
// AiService.java（调用方）
@Transactional(readOnly = true)                 // 调用方开了一个只读事务
public EventRecommendationResponse recommendEvents(...) {
    A: 读画像
    B: 召回活动
    C: 模型排序
    D: recommendationFeedbackService.recordImpressions(...)   // 调用另一个类的方法
    return 结果;
}

// RecommendationFeedbackService.java（被调用方，B1 新写的类）
@Transactional(propagation = Propagation.REQUIRES_NEW)      // 改动就是这一行
public void recordImpressions(...) {
    impressionRepository.saveAll(rows);
}
```

事务会顺着方法调用往下传。走到 D 时，只读事务还没结束，Spring 就要决定被调用的方法怎么处理事务，这就是**传播性**：

| 传播性 | 走到 D 时会发生什么 | 结果 |
|---|---|---|
| `REQUIRED`（不写时的默认值） | “外面已经有事务了，我加入它。”于是 D 也跑在只读事务里 | 写入失败 |
| `REQUIRES_NEW`（我们的写法） | “不管外面有没有事务，我都自己开一个新的。”外面的事务先暂停，D 在一个可写的新事务里执行，提交后再回到外面 | 写入成功 |

> 比喻：走出阅览室，去旁边的登记台写。

## 4. 领域事件

### 问题
预约之后要记一条“已预约”反馈。最直接的写法是在 `reserve()` 里直接调用推荐反馈服务。但这样一来，预约服务就得知道“推荐反馈”这件事；以后要加积分、通知、画像更新，每次都得改预约的代码。

### 领域事件的思路
业务代码自己把核心业务做完，然后**发一条公告，说明“发生了什么”**，并不关心谁会看到这条公告。

```java
// ReservationService.reserve()
保存预约; 生成二维码; 同步日程;                    // 核心业务仍然自己做
eventPublisher.publishEvent(
    RecommendationActivityEvent.forEvent(userId, eventId, RESERVED));   // 公告：某学生预约了活动 58
```

`RecommendationActivityEvent` 只是一个普通的数据对象：谁、哪个活动、做了什么动作。

### 你的理解，以及补充
> 你的理解：它原先负责整块业务逻辑，现在只负责发公告；至于谁收到公告做什么，可以写在别的服务里。

方向是对的。补充一点：**它不是只发公告**，预约服务自己的核心业务（保存预约、生成二维码、同步日程）还是自己做，交出去的只是**附带的后续动作**。

判断一件事该放在主流程里还是交给监听器，可以问自己：**这件事失败了，主业务是否也应该算失败？** 如果是，放主流程；如果不是，交给监听器。

### 和 RabbitMQ 的区别
这里的事件只在**同一个 Java 进程内部**传递（Spring 的 `ApplicationEventPublisher`），不经过网络，也不会被持久化。MQ 是跨进程的，消息会存起来。

## 5. 监听器：监听谁、做什么

**监听器**是一个“订阅了某种公告”的方法，公告一发出，Spring 就自动调用它。

```java
@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)
public void onActivity(RecommendationActivityEvent activity) {
    try {
        feedbackService.recordImplicit(activity);   // 查 7 天内的推荐，挂一条隐式反馈
    } catch (RuntimeException ex) {
        log.warn(...);                              // 失败了只记日志
    }
}
```

- **监听谁**：由方法参数的类型决定。参数是 `RecommendationActivityEvent`，它就只接收这一种事件。
- **谁发的**：`ReservationService`（预约、取消、完成）和 `FollowService`（新关注）。
- **做什么**：查这个学生 7 天内是否被推荐过这个活动，如果有，就记一条反馈。

```
ReservationService ──发布公告──▶ Spring ──转交──▶ RecommendationActivityListener ──▶ 写反馈
  （不知道谁在监听）                                  （只关心这一种公告）
```

**好处**：解耦。以后要加别的后续动作，就再写一个监听器，预约的代码一行都不用改。

## 6. 为什么要等预约真正成功之后才执行

`phase = AFTER_COMMIT`：**等发布公告的那个事务提交成功之后，才通知监听器。**

`reserve()` 是一个事务：① 查活动 ② 保存预约 ③ 生成二维码 ④ 同步日程 ⑤ 发布公告，最后提交。

| 情况 | 不等提交，立刻写反馈 | AFTER_COMMIT（我们的做法） |
|---|---|---|
| 一切正常 | 有预约，也有反馈 | 有预约，也有反馈 |
| 第 ④ 步失败，预约回滚 | **反馈已经写了，但其实没有预约**，数据是错的 | 事务没提交，公告根本不会送到，不写反馈 |
| 写反馈时出错 | 如果在同一个事务里，**学生的预约也跟着失败** | 预约早已提交，反馈失败只记一条日志 |

细节：
- 监听器执行时，预约的事务已经结束了，所以 `recordImplicit` 也标了 `REQUIRES_NEW`，自己开一个事务。
- `fallbackExecution = true`：如果有人在没有事务的地方发布了这个事件，监听器也照常执行。

### 你的总结，以及一个用词修正
> 你的总结：目的就是不让反馈影响主业务。只能是“主业务真、反馈假”，不能是“反馈真、主业务假”。

完全正确。只修正一个词：不是反馈“假”，而是反馈“**缺失**”。

- **可以接受**：预约成功了，反馈漏记了一条（数据少了）。
- **不能接受**：反馈说“已预约”，但其实没有预约（数据错了）；或者因为记反馈失败，导致学生预约不了。

少一条数据只是统计稍微不准，错一条数据会误导判断。AFTER_COMMIT 的保证是：**最多少记，绝不错记。**

## 7. 代价：AFTER_COMMIT 和 Outbox 的区别

在“预约已经提交”和“监听器执行”之间有一个很短的时间窗口。如果应用恰好在这时崩溃，内存里的事件就丢了，这条反馈也就漏记了。

| | AFTER_COMMIT 领域事件 | Outbox（我们 MQ 用的模式） |
|---|---|---|
| 消息存在哪里 | 只在内存里 | 和业务数据在**同一个事务**里写进一张表 |
| 应用崩溃后 | 消息丢失 | 消息还在表里，重启后继续投递 |
| 复杂度 | 很低 | 需要表、调度器、重试和幂等 |
| 适合的场景 | 统计、日志这类丢一条也无所谓的数据 | 评分、积分、计费这类一条都不能丢的数据 |

**怎么选，取决于这份数据丢一条的代价有多大。**

> 思考题：“预约成功后给学生发一条站内通知”应该用哪种方案？“预约成功后扣除一次免费名额”呢？

## 8. Spring 代理

### 比喻：明星和经纪人
你想请明星（真正干活的对象）演出，但只能联系他的**经纪人**（代理对象）。经纪人对外的样子和明星一模一样：
1. 唱之前，先签合同、收定金；
2. 转交给明星本人，明星唱歌；
3. 唱完之后，顺利就结账，出了状况就退钱。

“额外的流程”可以是开启和提交事务，也可以是缓存、异步执行等。

### Spring 具体做了什么
- **启动时**：发现某个类的方法上有 `@Transactional`，就给这个类生成一个代理对象。别的类注入它时，**拿到的是代理对象**。
- **运行时**（Spring 自动生成，伪代码）：

```java
class RecommendationFeedbackService$$Proxy extends RecommendationFeedbackService {
    RecommendationFeedbackService target;          // 明星本人

    @Override
    public void recordImpressions(...) {
        暂停外面的事务;  开启一个新事务;               // REQUIRES_NEW 在这里生效
        try {
            target.recordImpressions(...);          // 转交给真正的方法
            提交;
        } catch (RuntimeException e) {
            回滚;  throw e;
        } finally {
            恢复外面的事务;
        }
    }
}
```

注解本身什么都不做，它只是一个标记，**真正干活的是代理**。这就是 **AOP（面向切面编程）**：事务、日志、缓存这类横跨很多方法的通用逻辑，统一交给代理处理，业务方法里只剩下业务逻辑。

### 代理是怎么生成的

| 方式 | 原理 | 限制 |
|---|---|---|
| JDK 动态代理 | 生成一个实现同一接口的新类 | 目标类必须实现接口 |
| **CGLIB**（Spring Boot 默认） | 运行时生成目标类的**子类** | 只能重写允许重写的方法 |

推论：
- `final` 类不能被代理；
- `final` 方法和 `private` 方法上的注解不生效；
- 打印注入进来的对象的类名，会看到 `xxx$$SpringCGLIB$$0`。

**和项目的联系**：单元测试里“Mockito 不能 mock record”，原因一样。我们的 Mockito 配置成了 `mock-maker-subclass`，也是靠生成子类来造假对象，碰到 final 类就没办法。

### 代理还用在哪里

| 注解 | 代理在方法前后做的事 |
|---|---|
| `@Transactional` | 开启、提交、回滚事务 |
| `@Async` | 放进线程池异步执行 |
| `@Cacheable` | 先查缓存，命中就直接返回 |
| `@Retryable` | 出错后自动重试 |
| `@PreAuthorize` | 先检查权限 |

这些注解都有同样的坑：**同一个类里用 `this` 调用不生效，`private` 和 `final` 方法不生效。**

## 9. 自调用：问答和纠错

### 题目
1. 同一个类里，方法 A 没有注解，它用 `this.b()` 调用标了 `@Transactional` 的方法 B。外部调用 A 时，B 有事务吗？
2. 反过来：A 有注解，B 没有，B 有事务吗？

### 你的第一次回答
> 前者是 A 明星调用了 B 的经纪人，B 应该有事务；后者是 A 明星调用了 B 明星，所以 B 没有事务。

**两题都答反了，错在同一个地方：以为 A 和 B 是两个明星。**

### 纠正：A 和 B 是同一个明星的两项才艺
A 和 B 是**同一个类的两个方法**，整个类只有**一个明星、一个经纪人**。经纪人只拦截**从外面来的请求**。明星在台上唱着唱着，自己接着跳一段舞，不会回头去找经纪人。`this.b()` 里的 `this`，就是明星本人。

**第 1 题：B 没有事务。**
1. 外部调用 A，经过经纪人。A 没有注解，经纪人什么都不做，直接转交。
2. 明星执行 A，遇到 `this.b()`，**自己直接执行 B**，没有经过经纪人。
3. B 的注解要靠经纪人才能生效，而经纪人根本不知道 B 被调用了。

**第 2 题：B 有事务，就是 A 的那个事务。**
1. 外部调用 A，经纪人看到注解，开启事务。
2. 明星执行 A，遇到 `this.b()`，直接执行 B。
3. 这时 A 的事务还没结束，所以 B 的数据库操作自然就在这个事务里。

### 关键概念：事务挂在线程上，不挂在方法上
经纪人开启事务，相当于在当前线程上挂了一块“交易进行中”的牌子（Spring 内部用 `ThreadLocal` 实现）。在牌子被摘下之前，这个线程上的**所有数据库操作**，不管出自哪个方法、有没有注解，都算在这个事务里。

- **注解的作用**：让经纪人决定挂牌、换牌、摘牌（开启新事务、加入已有事务、提交或回滚）。
- **没有注解的方法**：不会改牌子，但只要牌子挂着，它的操作照样在事务里。

| 情况 | B 有事务吗 | 原因 |
|---|---|---|
| A 无注解，`this.b()`，B 有注解 | **没有** | 自调用绕过了经纪人 |
| A 有注解，`this.b()`，B 无注解 | **有（A 的事务）** | 事务挂在线程上 |
| B 在另一个类里，并且有注解 | **按 B 的注解** | 跨类调用经过 B 所在类的代理 |

### 回到项目
`recommendEvents` 挂上了“只读”的牌子。如果 `recordImpressions` 写在同一个类里、用 `this` 调用，就是第 2 种情况：它会跑在只读事务里，写入失败，写了 `REQUIRES_NEW` 也没用。所以要把它挪到另一个类，变成第 3 种情况。

自调用失效的三种解法：
1. **把方法挪到另一个 Bean**（我们的做法）；
2. 把自己的代理注入进来，再通过代理调用（可以用，但写法别扭）；
3. 用 `TransactionTemplate` 在代码里手动控制事务，不依赖代理。

---

## 10. 一句话总结

> **经纪人只拦外部调用；事务挂在线程上。**
> 代理是 Spring 在真实对象外面包的一层，你注入和调用的都是它，它在真正的方法前后执行注解所声明的逻辑。不经过代理的调用，注解就不生效。
