# B2：运维面板“推荐”分区（在线指标）

> 一句话：B1 开始记录推荐曝光和反馈之后，B2 把这些数据变成能直接看懂的指标，包括推荐次数、零结果率、反馈漏斗、每日趋势、“不相关”的原因，以及每次推荐展示了什么、学生怎么反应。上线第一眼就看到：**零结果率 42.9%**。
>
> **状态（2026-10-24）**：已完成。Maven 全量 168 个测试通过（新增 4 个），前端构建通过，真实环境里接口和页面都检查过（待人工验收）。

---

## 1. 指标口径：先把“分母”说清楚

| 指标 | 定义 | 为什么这样定义 |
| --- | --- | --- |
| 推荐次数 | 窗口内 `EVENT_RECOMMENDATION` 运行数 | 推荐量的基本盘 |
| 零结果率 | 成功的推荐中，一个活动都没推荐的占比 | 从运行摘要里的 `recommendationCount=0` 读取，**B1 之前的推荐也能统计** |
| 曝光 | 一次推荐展示的一个活动，算一次曝光 | 所有比率都以它为分母 |
| 感兴趣率 / 预约率 / 完成率 / 关注率 / 不相关率 | 带有该类反馈的曝光数 ÷ 曝光数 | 一次曝光被预约两次也只算一次，否则比率可能超过 100% |
| 主动反馈率 | 点过“感兴趣”或“不相关”的曝光占比 | 衡量反馈按钮有没有人用；太低的话，显式反馈的数据就不可信 |
| 因“不相关”被过滤 | 窗口内出现 `SUPPRESSED_BY_FEEDBACK` 的推荐次数 | 直接看 B1 那条规则有没有生效 |
| 每天 | 按东京时间的日期分桶；**反馈计在推荐展示的那一天** | 周一推荐、周三预约，算在周一。这样每天的比率描述的是“那天推荐的质量”，而不是“那天发生了多少动作” |

最后一条叫**按曝光归期**（cohort）。如果按动作发生的日期统计，推荐量很少的一天也可能因为前几天推荐的转化而显得“转化很高”，这会误导判断。

---

## 2. 关键设计决策

### D1：在 Java 里聚合，不写 SQL GROUP BY

**选项**：
1. 写 SQL 聚合（`GROUP BY DATE(shown_at)`）：性能好，但涉及时区换算（数据库是 UTC，业务是东京时间）；而且之前就发现过 JDBC 和 Hibernate 的时区处理不一致。
2. 用 JPQL 把窗口内的曝光和反馈取出来，在 Java 里聚合：时间由 Hibernate 统一读取，按东京日期分桶也很直接。

**选择**：2。现在的数据量是每天几十到几百条曝光，在内存里聚合完全没问题。聚合逻辑写成**纯函数**（`funnel()`、`daily()`），单元测试不需要数据库。等曝光达到每天几万条时，再改成预聚合表（每天定时汇总一行），那时纯函数的计算逻辑可以直接复用。

### D2：零结果率不依赖曝光表

零结果的推荐**根本不会产生曝光**，所以无法从曝光表里算出来。它是从运行记录的输出摘要里读的。这样还有一个好处：B1 上线之前的推荐也能统计。从历史数据看，零结果是一个长期存在的问题，不是最近才出现的。

### D3：“最近的推荐”把运行、曝光和反馈串在一起

每次推荐显示：需求原文、谁、耗时、展示了哪些活动（名次、分数）、每个活动收到了哪些反馈。点“运行 #”会跳到 Agent 运行详情，可以看完整 trace。“不相关的原因”里的“查看那次推荐”也能跳过去。**从一条差评一路查到当时的召回和重排过程**，这正是 B1 里给曝光记录运行 ID 的目的。

### D4：说明数据什么时候开始记录

页面上写明“曝光从 X 开始记录”；B1 之前的推荐显示“发生在开始记录曝光之前”，而不是一个空列表。否则看的人会以为那些推荐什么都没展示。**指标面板要说清楚自己的数据边界**，不然很容易被误读。

---

## 3. 上线第一眼看到的

- **零结果率 42.9%**（7 次推荐里有 3 次没推荐任何活动）。原因很清楚：线上只有活动 #58 没过期，其余 55 个都过期了。这不是推荐算法的问题，而是**活动供给不足**，属于运营问题。没有这个面板时，你在页面上只会看到“没找到合适的活动”，看不出是算法不行还是没有可推的活动。
- 历史推荐的平均耗时约 18 秒，查询改写和重排各调用一次模型。

---

## 4. 测试

- **漏斗**：一次曝光按类型只算一次；窗口外曝光的反馈不计入；比率的分母是曝光数（手算核对：4 次曝光、2 次预约 → 50%）；空窗口的比率是 0，不会出现除零错误。
- **每日分桶**：UTC 16:30 会归到东京时间的第二天；两天后的预约算在推荐展示的那一天；失败的运行计入推荐次数，但不算零结果。
- **从运行摘要读取推荐数**。
- 真实环境：用 `/api/ops/recommendations/stats` 和 `/runs` 调出的数字，与第 3 节一致；页面显示正常。

**没有覆盖的**：数据量大时的性能（当前规模不需要）；运营侧“活动供给”指标（例如未过期活动数），可以作为下一步加到总览里。

---

## 5. 可迁移的模式

1. **先定口径，再写代码**：分母是什么、怎么去重、算在哪一天，这三件事没定清楚，后面的数字都不可信。
2. **用 cohort 看质量**：反馈算在推荐展示的那一天，而不是动作发生的那一天。
3. **聚合逻辑写成纯函数**：好测试，以后改成预聚合也能直接复用。
4. **指标要标明自己的边界**：数据从什么时候开始记录，旧数据缺什么。
