## 一、用大白话说，这次做了什么

D4 之前，后端没有任何限流。一个学生可以无限次点“生成行动计划”，每点一次就要调用约 6 次模型，花的是真钱；登录可以无限次试密码。

D4 加了五样东西：

| 防什么 | 怎么防 |
|---|---|
| 成本失控 | AI 接口按账号限次数：每分钟一层、每天一层 |
| 服务被压垮 | AI 并发闸：同一个人同时最多 2 个 AI 请求在跑 |
| 暴力破解 | 同一个“账号 + IP”连续输错 5 次，锁 15 分钟；同一个 IP 每分钟最多尝试登录 20 次 |
| 刷注册 | 同一个 IP 每小时最多注册 5 个账号 |
| 心里没数 | 运维面板新增“限流”分区：今天调了多少次模型、预算用了多少、谁被限了几次 |

另外顺手修了一个漏洞：评测集接口原来没有任何鉴权，现在只有管理员能调。

## 二、关键决策

### 决策 1：接口分档，数值只写在一个地方

```java
AI_HEAVY("重 AI 功能", USER, 并发闸, 每分钟 3, 每天 30)
AI_LIGHT("AI 功能",    USER, 并发闸, 每分钟 10, 每天 100)
EVENT_SUBMIT("提交活动审核", USER, 每天 20)
REGISTER("注册", IP, 每小时 5)
LOGIN("登录", IP, 每分钟 20)
```

数值全部写在 `RateLimitTier` 这一个枚举里，接口上只标档位：

```java
@PostMapping("/action-plans")
@RateLimited(RateLimitTier.AI_HEAVY)
public ... recommendPlans(...)
```

和 D1 的 `@RequirePermission`、D2 的转移表是同一个思路：**规则集中在一处，使用的地方只做声明**。以后新增一个 AI 接口，加一行注解就行。

| 档位 | 接口 |
|---|---|
| 重 AI | 活动推荐、行动计划、引导对话 |
| AI | 自我分析、引导动作判断、教练对话、生成教练日志、简历解析 / 出题 / 回答、能力评估、能力评审开始 / 提交、能力晋升评审开始 / 提交、Agent 差评反馈、检索调试 |

### 决策 2：“提交活动审核”挂在状态机入口，不挂在接口上

组织新建、修改、提交活动，有时会触发 AI 审核，有时不会（只保存草稿、已经转人工）。如果把限流挂在接口上，存一次草稿也会被算一次。

所以这一档没有标在接口上，而是放在 D2 的状态机入口 `EventLifecycleService.transition` 里：

```java
if (要进入“审核中”) && (操作者是组织) && (这次会交给 AI) {
    rateLimiter.consume(EVENT_SUBMIT, 组织账号);
}
```

**只有真正把活动送去 AI 审核的那一步才算一次**。D2 把所有状态变化收口到一个入口，现在加规则也只用改这一处。超限时整个事务回滚，活动状态不变。

### 决策 3：固定窗口，分钟和天两层

时间切成一格一格的：每分钟一格、每天一格。每一格在 Redis 里有一个计数器，名字带着格子的编号，格子结束时计数器自动过期。

```
rl:AI_HEAVY:m:<学生>:<第几分钟>   → 3
rl:AI_HEAVY:d:<学生>:<第几天>     → 17
```

- **先查短的窗口，再查长的**：一分钟内连点 50 次，被拦下的 47 次不会扣掉当天的额度。
- **“一天”按东京时间算**（与项目里其他按天统计的地方一致），零点重置。
- **“加一，新键就设过期”用 Lua 脚本**：Redis 执行脚本时不会插进别的命令，所以不会出现“加了一但没设过期，计数器永远不消失”的情况。

### 决策 4：并发闸

次数限制管“总共用了几次”，并发闸管“同一时刻有几个在跑”：

- 请求开始时计数加一，已经是 2 就直接拒绝；
- 请求结束时（不管成功还是失败）减一，用 Java 的 `try-with-resources` 保证一定执行；
- 程序中途崩溃没来得及减：计数器 5 分钟后自动过期。之所以设 5 分钟，是因为行动计划要连续调用好几次模型，每次最多 30 秒。

重 AI 和普通 AI 共用同一个闸。

### 决策 5：登录锁“账号 + IP”，不锁账号

只锁账号的话，坏人故意替别人输错 5 次，真正的主人就登不进去了。锁“账号 + IP”，主人换个网络照样能登。

- 15 分钟内输错 5 次，锁 15 分钟；第 5 次输错直接返回“已锁定”，不再返回“密码错误”；
- 登录成功清零；
- 账号不存在也算一次失败，否则攻击者可以从回复的不同判断账号是否存在。

### 决策 6：Redis 挂了就放行

登录态本来就存在 Redis 里。Redis 一挂，所有登录都会失效，网站已经不能用了。限流这一层再拒绝所有请求也没有意义，所以选择放行并记一条警告日志。

### 决策 7：全站模型调用总数只显示，不暂停

`OpenAiCompatibleLlmClient` 每真正发出一次请求，就在 Redis 里给当天的计数加一（对话和向量分开计）。运维面板显示“今天调了多少次 / 预算多少”，超了标红，但不会暂停任何功能。预算的数值用环境变量 `AI_DAILY_MODEL_BUDGET` 设置，默认 2000。

### 决策 8：拿到真实 IP

部署在 nginx 后面时，后端看到的来源地址永远是 nginx。开启 `server.forward-headers-strategy=native` 之后，Tomcat 会读 nginx 传过来的 `X-Forwarded-For`，而且只在请求来自内网代理时才读，公网上的人不能伪造。见 PROBLEM_LOG 第 072 条。

## 三、超限时用户看到什么

返回 429，带标准的 `Retry-After` 头（还要等多少秒）。提示文字写在返回内容里，前端原有的错误提示直接显示：

| 情况 | 提示 |
|---|---|
| 每分钟超限 | AI 功能太频繁（每分钟最多 10 次），请 42 秒后再试 |
| 每天超限 | 今天的重 AI 功能次数已用完（每天最多 30 次），明天再来吧 |
| 并发闸 | 你有 2 个 AI 请求还在处理，请等它们完成后再试 |
| 登录锁定 | 密码连续输错 5 次，请 15 分钟后再试 |

按你选的 A：平时不显示剩余次数，只在超限时提示。

## 四、怎么证明它是对的

### 单测（新增 12 个，全量 243 个通过）

- `RateLimiterTest`（7 个）：
  - 每分钟超限后返回剩余秒数，下一分钟恢复，别人不受影响；
  - 一分钟内被拒绝的请求不扣当天额度，当天用完后提示“明天再来”，等待时间算到东京时间零点；
  - “一天”按配置的时区切换，而不是按 UTC；
  - 并发闸：两个占满后第三个被拒，关掉一个就能再进；
  - 没释放的名额会过期；
  - 被拒绝的次数被记下来，供运维面板读取；
  - Redis 不可用时全部放行。
- `LoginGuardTest`（3 个）：
  - 第 5 次输错就锁定，换 IP 不受影响，15 分钟后解锁；
  - 登录成功清零；
  - 15 分钟之前的失败会被忘掉。
- `EventLifecycleServiceTest`（新增 2 个）：
  - 只有“组织把活动送去 AI 审核”才扣额度，转人工和运营重新分析不扣；
  - 额度用完时，活动状态、审核消息、状态历史都不变。

测试用一个内存版的计数存储（`InMemoryRateLimitStore`），跟 Redis 版实现同一个接口，过期时间由测试时钟控制，不需要真的 Redis。

## 五、真实启动

2026-11-03 在 8081 端口启动，把模型设成 mock（不花钱）。启动成功，数据库无需迁移（D4 没有新表，计数都在 Redis 里）。用脚本跑了 17 项，全部符合预期：

- **登录**：同一账号连续输错 4 次返回 401，第 5 次返回 429，提示锁 15 分钟，`Retry-After: 900`；再试仍是 429。
- **AI 接口**：新学生连续调 10 次自我分析都成功，第 11 次返回 429，提示还要等几秒，`Retry-After` 与提示一致（34 秒）。
- **评测集**：学生调用返回 403；管理员调用返回 404（开关是关的，说明已经通过了权限检查）。
- **限流统计**：学生读不到（404，运维面板不对学生开放）；admin_zero 读到今天的统计：登录锁定 1 次、AI 功能被拒 1 次，模型调用 0 次（mock 不计数），预算 2000。
- **活动提交**：新组织提交活动成功，状态是“审核中”，说明限流不影响正常提交。
- **Redis 视图**：运维面板能看到新的键族 `rl:*`（8 个）和 `ai:calls:*`。

**本地数据库里留下了测试数据**：学生账号 `d4stu_` 开头、组织账号 `d4org_` 开头和一个审核中的测试活动。

**没有覆盖到的**：
- 并发闸：mock 模型回答太快，同时占不住两个名额，只有单测；
- 每天的额度：要等一整天，只有单测；
- 前端页面没在浏览器里点过（类型检查和构建通过）。

## 六、已知边界与后续

- **固定窗口的交界处**：12:00:59 和 12:01:00 各连发一次，两秒内能用掉两分钟的额度。每天一层兜底，总量跑不掉。
- **数值写在代码里**：改数值要重新部署。要在运行时调整，以后可以挪进配置。
- **多个账号**：一个人注册多个账号，每个账号各有一份额度。注册已经按 IP 限了，但换 IP 就挡不住。
- **注册限流在学校网络下**：同一栋楼的学生可能共用一个出口 IP，开学注册高峰时可能被误伤。真遇到再调高。
- **异步链路不限**：签到、完成挑战在后台触发的评估不受限制（已经有去重）。
- **旧版能力聚类**：每打开一次就可能调一次模型，但前端已经不用这个页面了，D4 不处理，记在待办里。
- **被限流的统计**只保留 8 天，没有写进数据库。

## 七、可迁移的模式

1. **规则集中，使用处只声明**：数值都在一个枚举里，接口上只写档位。
2. **把限流放在“真正花钱的那一步”**：活动提交不限接口，只限“送去 AI”这一个状态变化。
3. **次数限制 + 并发闸**：一个管总量，一个管同一时刻。只有前者挡不住慢请求占满线程。
4. **限流对象选得能被“替别人用”时不伤人**：登录锁“账号 + IP”，不锁账号。
5. **读改写一步完成**：计数和设过期放在同一个 Lua 脚本里。
6. **依赖挂了时怎么办，取决于它挂了以后系统还剩什么**：登录态也在 Redis，所以放行。
7. **存储抽成接口**：生产用 Redis，测试用内存版，规则可以不依赖外部服务来验证。

### 面试怎么讲（STAR）

- **S**：平台约 20 个接口会同步调用大模型，单个请求最多约 6 次调用，每次最长 30 秒；没有任何限流，登录也不防暴力破解。
- **T**：在不改业务代码的前提下，控制模型成本，防止慢请求占满线程，并防住暴力破解。
- **A**：
  - 接口分档，自定义注解加 AOP 实现限流；
  - 用 Redis 固定窗口（每分钟 + 每天两层，Lua 脚本保证原子性）；
  - 再加按用户的并发闸；
  - 活动提交的额度放在状态机入口，只在真正送去 AI 时计数；
  - 登录按“账号 + IP”锁定；
  - Redis 故障时放行；
  - 运维面板展示当天的模型调用量和被限流的对象。
- **R**：所有 AI 接口都有了次数和并发上限，单个学生每天最多约 30 次重请求；登录 15 分钟内最多试 5 次；新增接口只需一行注解。
