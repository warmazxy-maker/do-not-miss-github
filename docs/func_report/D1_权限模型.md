# D1：权限模型（RBAC + AOP 统一校验 + 审计日志）

> 一句话：之前后端**从不检查角色**，学生端和社会端只靠前端路由区分。现在有了完整的“权限 → 角色 → 用户”三层模型：**权限**定义在代码里，**角色**存在数据库里（新增角色只需加数据），每个用户只有一个角色。接口上加 `@RequirePermission` 注解，由一个 AOP 切面统一校验，并把敏感操作和所有被拒绝的尝试写进审计日志。另外新增了超级管理员 `admin_zero` 和组织成员关系。
>
> **状态（2026-10-26）**：已完成。Maven 全量 202 个测试通过，前端构建通过。**Docker 没开，没在真实 MySQL 上跑过 V32 迁移**，下次启动后端时要留意迁移是否成功（待人工验收）。

## 2. 关键设计决策

### D1：权限写在代码里，角色存在数据库里

**为什么这样分**：代码里判断的是“有没有审核权限”，而一个新权限总是伴随一个新功能出现，新功能本来就要改代码，所以权限就定义在代码里（`Permission` 枚举）。角色只是“权限的组合”，组合会经常调整，所以角色和角色拥有的权限存在数据库里（`roles`、`role_permissions` 两张表）。

**这就是你要的“扩展接口”**：想要一个“既能审核又能用学生功能”的新角色，只需在 `roles` 里插一行，再在 `role_permissions` 里插两行，**一行 Java 代码都不用改**。

`users.role` 上加了外键，指向 `roles.code`，数据库保证每个用户的角色一定存在。

### D2：AOP 统一校验，而不是每个接口手写 if

```java
@RequirePermission(value = Permission.EVENT_REVIEW, action = "event.approve")
public Map<String, String> approve(@PathVariable Long eventId) { ... }
```

接口方法上只写一个注解。`PermissionAspect` 在代理里拦截调用，依次执行：
1. 识别调用者（没登录 → 401）；
2. 检查角色有没有注解要求的**任一**权限（没有 → 403，**一定记审计**）；
3. 执行真正的方法；如果是写操作，并且权限标记为需要审计，就把结果（成功 / 失败）写进审计日志。

**这正是之前学的代理和 AOP**：Spring 给每个带注解的控制器生成一个代理，切面在真正的方法执行前后插入自己的逻辑。业务代码里一行权限判断都没有。

**注解可以放在类上**：学生功能的 15 个控制器都是在类上加了 `@RequirePermission(Permission.STUDENT_FEATURES)`，类里所有方法都生效；方法上的注解会覆盖类上的。

**原来“组织账号也能调学生接口”**，现在会返回 403，这是你定的“权限做了就要按设计来”。

### D3：注解表达不了的规则，留在代码里

“组织只能对**自己发布的**活动重新分析”，这个判断依赖数据，看了活动的发布者才知道，注解做不到。所以分两层：
- 注解：`@RequirePermission({EVENT_PUBLISH, EVENT_REVIEW})`，先挡掉学生和匿名用户，同时负责审计；
- 代码（`EventReviewAccess`）：审核员可以操作任何活动；组织必须是该活动的发布者。

**这是权限设计里的常见分工**：“你是什么角色”用声明式（注解），“你和这条数据是什么关系”用编程式（代码）。

### D4：审计日志记什么

- **被拒绝的尝试一律记**（包括未登录）：反复越权本身就是需要关注的安全信号。
- **成功的写操作，只记标记为“需要审计”的权限**：发布活动、审核、运维操作、授予角色。学生功能不记，否则每次 AI 对话都会写一条日志，没有意义。
- **只读操作不记**。
- 审计写入在**独立事务**里执行，并且吞掉自身的异常。被拒绝的请求虽然失败了，审计记录也必须留下；审计表出问题，也不能拖垮被审计的操作。这和 B1 的反馈记录是同一个原则。
- 管理员可以在 `GET /api/ops/audit-logs` 查看（需要 `AUDIT_VIEW`），前端页面留到 D3。

### D5：超级管理员的密码不能进仓库

**问题**：最直接的做法是在迁移脚本里插入一个 `admin_zero` 账号，但密码哈希就会进入**公开的 GitHub 仓库**。

**选择**：`AdminZeroBootstrap` 在后端启动时检查：
- 账号不存在，并且本地 `.env` 里有 `ADMIN_ZERO_PASSWORD`（至少 12 位），就用 BCrypt 加密后创建账号；
- 账号已经存在：**不改密码**，只确保它的角色仍然是 `ADMIN_ZERO`（防止被误改）；
- 没有配置密码：什么都不创建。

我已经生成了一个 20 位的随机密码，写进你本地的 `do-not-miss-backend/.env`（`ADMIN_ZERO_PASSWORD`）。这个文件不会提交，密码也没有在聊天里出现。登录账号是 `admin_zero`。

**目前这是产生管理员的唯一方式**：没有任何接口可以授予管理员角色，`ROLE_ASSIGN` 权限也暂时没有对应的接口。

### D6：注册时不能自己选高权限角色

`roles` 表里有一列 `self_registrable`，只有学生和组织是 `true`。注册时会查这张表，选了其他角色就返回 400。**原来的代码会接受任何存在的角色名**，如果不改，加了管理员角色之后，谁都能把自己注册成管理员。

### D7：运维面板的两道门

- **总开关** `OPS_CONSOLE_ENABLED` 保留：可以一键对所有人关闭，不用改任何角色，这叫**纵深防御**；
- **白名单** `OPS_ADMIN_USERS` 删除，换成“角色有没有 `OPS_CONSOLE_VIEW`”。

评测候选的审核接口只检查总开关，加上 `EVAL_CANDIDATE_REVIEW` 权限，不要求能看运维面板，因为运营没有运维面板的权限。不过运营的审核页面要到 D3 才有，目前它在运维面板里，只有管理员能点到。

### D8：组织成员关系，以及有意保留的缺口

- 新增 `organization_members` 表：一个组织可以有多个账号。
- 发布活动时调用 `OrganizationMembershipService.ensureCanPublish`：
  - 已经是成员：直接通过；
  - 组织还没有成员：记为 `CLAIMED`（第一个发布者认领了它）；
  - 组织已有其他成员：**仍然放行**，记为 `AUTO_JOINED`，并打一条警告日志。
- **这就是你说的“先搭一个没有安全性的框架，把缺口留着”**：冒充问题还在，但规则集中在这一个方法里。以后要补（邀请码、运营审批、拒绝 `AUTO_JOINED`），只改这一个地方。
- 迁移时，根据“谁在哪个组织名下发布过活动”自动推断成员关系，记为 `INFERRED`（只针对组织账号）。

## 3. 一次请求的路径（以“运营通过一个活动”为例）

1. `POST /api/events/58/review/approve`，带着运营的 token。
2. Spring 先调用控制器的**代理**，`PermissionAspect` 拦截：
   - 读出方法上的注解，要求 `EVENT_REVIEW`；
   - `AccessService.current()`：token → Redis → 用户 ID → `users.role = OPERATOR` → 角色权限（缓存 60 秒）→ `{EVENT_REVIEW, EVAL_CANDIDATE_REVIEW}`；
   - 有这个权限，执行真正的 `approve()`。
3. `approve()` 修改状态、发布索引消息（这部分逻辑不变）。
4. 切面判断这是一个需要审计的写操作，在独立事务里写一条审计记录：`op-1 / OPERATOR / EVENT_REVIEW / event.approve / ALLOWED`。

如果换成学生来调：第 2 步发现没有权限，返回 403，并写一条 `DENIED` 的审计记录。

## 4. 测试与验证

**新增 24 个单元测试**（删除了 9 个被替代的旧测试）：
- **切面**：方法上的注解覆盖类上的；缺少权限时返回 403 并记审计，真正的方法不会执行；未登录返回 401 并记审计；成功的写操作记为 ALLOWED；方法抛异常时记为 FAILED，异常照常抛出；读操作和不需要审计的权限不记日志；审计写入失败不影响请求。
- **权限服务**：权限来自角色，未知的权限名被忽略；角色权限缓存 60 秒（用可控的时钟测试）；用户的角色每次请求都重新读取，所以改角色立即生效；匿名用户没有任何权限。
- **超级管理员**：用配置的密码创建，密码经过 BCrypt 加密；没有密码或密码太短时不创建；已有账号不改密码，但会恢复角色。
- **注册**：默认是学生，可以选组织；不能选高权限角色或不存在的角色。
- **组织**：已是成员时不新增记录；第一个发布者 `CLAIMED`，之后的 `AUTO_JOINED`。
- **审核访问**：审核员可以操作任何活动；组织只能操作自己发布的活动；学生即使是活动的创建者也不行；匿名用户在查询数据库之前就被拒绝。

**没有覆盖的**：
- **V32 迁移没有在真实 MySQL 上执行过**（Docker 没开）。外键要求 `users.role` 的现有值都在 `roles` 里，应该只有 STUDENT 和 SOCIAL 两种。
- 前端只做了构建检查，没有在浏览器里点过。

## 6. 可迁移的模式

1. **会频繁变化的放数据库，伴随代码变化的放代码**：角色放数据库，权限放代码。
2. **声明式管“你是谁”，编程式管“你和这条数据的关系”**。
3. **横切逻辑交给 AOP**：权限和审计都在切面里，业务代码保持干净。
4. **秘密不进仓库**：初始管理员靠“启动时读取本地配置”来创建，而不是写在迁移脚本里。
5. **纵深防御**：总开关加角色权限，两层互相独立。
6. **有意保留的缺口要集中、要可见**：放在一个方法里，写清楚注释，留下日志。

## 7. STAR

- **S**：后端从不检查角色，审核接口匿名可调用，注册时可以自选角色，运维面板靠环境变量白名单控制。
- **T**：建立可扩展的权限体系，覆盖全部敏感接口，并留下审计记录。
- **A**：采用“权限（代码）→ 角色（数据库）→ 用户（一人一个角色）”三层模型；用自定义注解加 AOP 切面统一校验和审计；数据相关的授权留在代码里；超级管理员由启动时读取本地配置创建，密码不进仓库；注册只允许可自助注册的角色；保留运维总开关；组织成员关系先记录、不验证，并把缺口集中在一个方法里。
- **R**：全部敏感接口纳入权限控制，被拒绝的尝试都会留下审计记录；新增角色不需要改代码；新增 24 个测试，全量 202 个通过。
