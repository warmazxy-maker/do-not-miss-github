## 一、用大白话说，这次做了什么

Tandem 以前只能“看”，现在能“替你做”四件事：**加日程、改日程、建挑战、预约活动**。但它自己一样都不会直接做：

- 模型决定要做某件事时，后端不执行，而是生成一张**确认卡片**，挂在 Tandem 这条回答下面。
- 卡片上写的是后端从数据库查出来的真实信息，比如活动名、主办方、时间、地点、和你日程冲突的提醒，而不是模型自己的描述。
- 只有你点卡片上的“确认”才执行，而且执行的就是卡片上那份内容，中间不再经过模型。
- 执行之后，卡片上有“撤销”按钮，可以把这次改动恢复原样（这是你在讨论中坚持加上的“版本回滚”）。撤销前会检查：如果你之后手动改过结果，撤销会拒绝，不会覆盖你的修改。
- 卡片 24 小时内有效。你想改一张还没确认的卡片，Tandem 会出一张新的，旧的自动作废。一次要做几件事就出几张卡片，可以“全部确认”。

## 二、整体结构

```
Tandem（模型）调用 reserve_event(event_id=65)
        │
        ▼
ToolExecutor（F0 的结构检查：白名单、开关、参数、权限、限流）
        │ 这个工具是 ConfirmableTool → 不执行，转给待确认服务
        ▼
PendingActionService.propose
   ├─ tool.propose()：第一遍检查（活动能不能约、是不是已经约过），只读不写
   │    └─ 做不了 → 返回 ERROR，不出卡片，Tandem 如实告诉你原因
   ├─ 存一行 agent_pending_actions（状态 PENDING，冻结的参数 + 卡片内容，24h 过期）
   └─ 返回 PENDING_CONFIRMATION 给模型：“卡片已生成，还没执行，不要说已经做好了”
        │
        ▼
回答保存时带着 run_id → 页面按 run_id 把卡片挂在这条回答下面

你点“确认” → POST /api/agent-actions/{id}/confirm
   在同一个数据库事务里：
   ├─ 状态 PENDING → DONE（比较后再交换，只有一次点击能赢）
   ├─ tool.apply(冻结的参数)：调用现有服务，服务自己再检查一遍（第二遍检查）
   └─ 记下撤销需要的信息（建出来的 id + 刚建好时的样子）
   任何一步失败 → 整个事务回滚 → 再单独把状态记为 FAILED 和原因

你点“撤销” → POST /api/agent-actions/{id}/undo
   同一个事务里：DONE → UNDONE，tool.undo() 先比对“现在的样子 == 刚执行完的样子”，一致才恢复
   不一致 → 回滚，卡片保持“已执行”，告诉你为什么没撤销
```

## 三、关键决策

### 决策 1：写入工具“只出卡片、不执行”，由架构保证，而不是靠提示词

最重要的一条：模型就算想直接执行也做不到。执行器看到 `ConfirmableTool` 只会调用 `propose`，它的 `execute` 方法直接抛异常；注册表在启动时还会校验，标成“需确认写入”的工具不实现这个接口，后端就起不来。能执行的只有 `/api/agent-actions/{id}/confirm`，而这个接口只能由学生的登录会话调用。

### 决策 2：卡片内容来自数据库，执行的是冻结的参数

- **卡片内容来自数据库**：预约卡片按活动 id 查数据库，写出真实的标题、主办方、时间和地点。就算模型把 id 弄错了，你看到的也是那个 id 对应的真实活动，能当场发现。
- **执行用冻结的参数**：生成卡片时把参数存进 `payload_json`；确认时只按这份执行，不再调用模型。

### 决策 3：两遍检查（你说“可以核查两遍，能减少工具调用失败”）

- **第一遍，出卡片时**：活动是否上架、是否已结束、你是否已经约过或参加过、结束时间是否晚于开始时间、要改的日程是否存在、改完是否和原来一样。做不了就不出卡片，Tandem 直接告诉你原因。
- **第二遍，点确认时**：现有服务照常检查（规则和页面上完全一样，没有任何特权），工具自己也会补查。
- **不拦、只提醒的**：和已有日程时间重叠、开始时间已经过去。卡片上用黄色提醒，因为冲突不一定是错，比如你本来就打算早退。

### 决策 4：版本回滚（你的决定：模型能改系统，就必须能回滚）

每个写入工具都必须写 `undo`。回滚有三条原则：

1. **只回滚这一次做的事。**比如预约：如果你原来就约过，后端根本不会出卡片，因为现有服务碰到“已约过”会直接返回原来那条预约，回滚时就会误取消一条不是这次做的预约。
2. **只在结果没被动过时回滚。**执行完立刻记一份“刚做完时的样子”（快照）；撤销时先比对，现在的样子和快照不一致就拒绝，告诉你“加上之后被改过了，为了不覆盖你的修改，没有撤销”。这就是乐观锁的思路。
3. **回滚尽量恢复成“没发生过”。**

| 工具 | 执行 | 回滚 | 拒绝回滚的情况 |
| --- | --- | --- | --- |
| 加日程 | 新建一条“自己添加”的日程 | 删除这条（和页面上删除一样） | 已经不在了；之后被改过 |
| 改日程 | 先确认它还是出卡片时的样子，再改 | 改回原样 | 改完之后又被改过 |
| 建挑战 | 新建挑战 | **真删除**（不是“已取消”，否则挑战列表里会留一条） | 已完成或已取消；被改过；日程里有关联它的安排 |
| 预约活动 | 预约，并自动加进日程 | 取消预约，日程里那一项也删掉 | 已取消或已完成；之后又重新约过 |

“改日程”在确认时也用快照：如果出卡片之后你在日程页改过这条，确认会失败，不会用旧卡片覆盖你的修改。

**撤销不了的副作用**：预约和取消会各发一条推荐反馈事件（“预约了”“取消了”），这两条会留在推荐系统里，属于真实发生过的行为记录，所以没有抹掉。

### 决策 5：状态机和“只有一次点击能赢”

```
PENDING ──确认成功──▶ DONE ──撤销成功──▶ UNDONE
   │                  └──撤销被拒：保持 DONE
   ├──确认失败──▶ FAILED
   ├──取消──▶ CANCELLED
   ├──超过 24h / 清空对话──▶ EXPIRED
   └──出了替换它的新卡片──▶ SUPERSEDED
```

每次状态变化都是一条带条件的 UPDATE：`… set status = 新状态 where id = ? and user_id = ? and status = 旧状态`，返回 1 才算赢。MySQL 执行 UPDATE 时会给这一行加锁，所以第二次点击会等第一次提交，然后发现状态已经变了，返回 0。确认时，状态变化和真正的写入在**同一个事务**里：写入失败，状态也一起回滚，不会出现“状态说做了，其实没做”或“卡在执行中”的情况。

### 决策 6：过期是“懒”的

不跑定时任务。数据库里的状态还是 PENDING，但页面显示和点击时都会按 `expires_at` 判断。点击时发现已经过期，就当场把状态改成 EXPIRED。好处是少一个定时任务。代价是数据库里会有一些“名义上还在等、实际已过期”的行，统计时要按过期时间判断（F5 做统计时要注意）。

### 决策 7：Tandem 怎么知道卡片后来怎样了

你点按钮时 Tandem 不会被叫醒（讨论第 1 点）。下一轮对话时，每条带卡片的旧回答前面会加一条系统记录，例如：“第 5 号 预约活动「留学生日语会话角」——已撤销（预约已取消……）。已撤销＝学生撤回了，结果已经恢复原样，等于没做……以这里和工具查到的为准”。最后这句是验收时补上的，见第四节。

## 四、验证中发现并修复的问题

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| 撤销预约时比较“预约时间”可能误判 | Java 的时间精确到纳秒，MySQL 存到微秒并且会四舍五入，同一个时间存进去再读出来不相等 | 允许 1 毫秒以内的误差（单测覆盖） |
| Tandem 把已撤销的日程说成还在（PROBLEM_LOG 076） | 模型沿用了自己上一条回答里的说法，没信“已撤销”的记录，也没信刚查到的日程（查日程明明返回 1 条） | 系统记录写明每个状态的含义；提示词加一条“旧回答里说的情况可能已经变了，以系统记录和刚查到的为准”。复测通过 |
| 撤销成功的提示显示了两遍 | 卡片的结果行和点击提示都显示了同一句 | 成功时只显示结果行 |
| 文字“这张卡片已经已执行了” | 状态名本身带“已” | 改成“已经处理过了（已执行）” |

## 六、从架构师角度要注意的工程点

1. **安全边界放在架构里，不放在提示词里。**“模型不能直接改数据”由接口类型、执行器分支和启动校验三层保证，提示词只负责让它说话得体。以后加任何写入工具，只要标成“需确认写入”，就自动走卡片流程；忘了实现回滚，后端直接起不来。
2. **“你看到的就是会执行的”。**卡片由后端从数据库生成，执行用冻结的参数，中间不经过模型。这是防止模型“说一套做一套”的关键，也顺带防住了提示注入：网页或活动描述里藏的指令最多让模型提出一张奇怪的卡片，而卡片上写的是真实内容，最后决定的是人。
3. **幂等和并发：状态机加条件更新。**不用分布式锁，也不用 Redis，靠数据库一条带条件的 UPDATE 加行锁就够了。前提是**状态变化和业务写入在同一个事务里**，否则会出现“状态说做了，其实没做”。代价是这个事务里调用的服务（预约、日程）都必须加入同一个事务、不能自己开新事务；以后要接的服务如果是异步的（比如发消息队列），这个模式就要换成“先记录、再补偿”。
4. **回滚不是“反向操作”这么简单。**
   - 要区分“这次做的”和“本来就有的”（预约那个例子）。
   - 要防止覆盖人的修改（快照比对，也就是乐观锁）。
   - 要分清哪些能回滚、哪些不能，比如推荐反馈事件和已经发出的通知。
   - 以后接“发消息”“通知别人”这类工具时，它们本质上撤不回来，回滚只能做“补偿”（再发一条更正），确认卡片上要写清楚“这件事做了就撤不回”。
5. **两遍检查都是必要的。**第一遍让体验好：不会出一张点了必然失败的卡片。第二遍保证正确：从出卡片到点确认之间，世界可能已经变了（活动下架、名额满了、你在别处改了日程）。“改日程”要求确认时日程还是出卡片时的样子，就是这个道理。
6. **超时和“孤儿卡片”。**出卡片受工具的 15 秒超时限制。如果查库特别慢、超时后卡片才存进去，模型会以为失败了，但卡片仍然会因为带着运行 id 出现在回答下面。这不会造成错误执行（仍然要人点），只是说法和卡片对不上，概率很低，先记下。
7. **模型对“状态变化”的理解不可靠（076 的教训）。**把状态告诉模型还不够，要讲清楚每个状态意味着什么，并明确“旧的说法可能过时”。更根本的办法是 F5 的评测里加一类用例：卡片撤销或取消之后，再问相关的问题。
8. **可观测性已经铺好，F5 可以直接用。**每张卡片的提出、确认、取消、过期、撤销、撤销被拒都作为运行记录挂在对应那次运行下面，包括参数、卡片内容和原因。“采纳率”和“撤销率”可以直接从 `agent_pending_actions` 按工具和提示词版本统计（注意懒过期，见决策 6）。
9. **数据量和清理。**`agent_pending_actions` 只增不减，清空对话只会作废未确认的卡片，不删行（为了审计和撤销）。以后需要按时间归档，比如半年前的、状态为终态的行。
10. **新增依赖方向。**`agentkit/tools` 现在直接依赖日程、挑战、预约的仓库（Repository），用来读当前的样子做快照比对。这比只调服务更“近”一层：以后这些表的结构变化，要记得同步检查回滚逻辑。

## 七、你来验收

1. 在 Tandem 里让它加一个日程、建一个挑战、预约一个活动，看看卡片上的信息对不对。
2. 点确认，再到对应页面看结果；回来点撤销，看是否恢复原样。
3. 试一下：确认后先到日程页改一下那条日程，再回来撤销，应该会被拒绝。
4. 说“好的”或“确认”，应该什么都不会执行，Tandem 会提醒你点按钮。
