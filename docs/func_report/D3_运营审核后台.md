## 一、用大白话说，这次做了什么

D2 把活动的状态变化收口成了一扇门（状态机），但门的另一边没有人：AI 连续三次要求修改之后转给人工的活动，没有页面能处理。D3 给运营搭了一个工作台：

| 谁 | 在哪 | 能做什么 |
|---|---|---|
| 运营 | `/operator` 运营后台 | **审核队列**：处理转人工的活动，点“抽检”复查 AI 通过的活动 |
| | | **活动管理**：查看所有活动，下架、重新上架、看历史 |
| | | **评测候选**：从运维面板搬过来，B4 的差评转评测用例 |
| 管理员 | `/ops` 运维面板 | 新增“审计日志”分区；运营后台入口 |
| 超级管理员 admin_zero | `/ops` 运维面板 | 新增“运营账号”分区：新建运营账号 |
| 组织 | 侧边栏“我的事件” | 小红点：AI 或运营动过你的活动 |

**一个重要的结构判断**：D3 **没有新增任何改状态的逻辑**。通过、要求修改、下架、重新上架，全部调用 D2 的接口，走 D2 的状态机。D3 只负责“给谁看什么”：队列、详情、列表。抽检“有问题”也是调用 D2 的下架。这就是 D2 单一入口的好处：**加一个新界面，不用加新的改状态的代码**。

## 二、关键决策

### 决策 1：一个队列，两种来源

```
审核队列 = 转人工（PENDING_REVIEW + route=MANUAL） ∪ 抽检（event_spot_checks 中 PENDING 的）
          按“开始等待的时间”先来先审
```

- **转人工**的等待时间：最近一次进入“审核中”的时间，从状态历史里取；
- **抽检**的等待时间：被抽出来的时间。

两种来源合并后统一按时间排序。运营只盯一个地方。

### 决策 2：抽检是“加一张小表”，不是“加一个状态”

可以有两种做法：

- 给活动加一个状态“抽检中”：要改 D2 的状态机，而且抽检期间学生看不到这个活动；
- **加一张 `event_spot_checks` 表**：活动状态不变，只记录“谁在什么时候抽了它，结果如何”。

选第二种。抽检是**对活动的一次观察**，不是活动生命周期的一个阶段。表上有 `UNIQUE(event_id)`，保证同一个活动只会被抽一次。

**抽哪几个**：

```sql
最近一次进入“已上架”的那条状态历史，动作是 AI_APPROVE
并且现在仍是已上架、没结束、从没被抽过
按那次通过的时间倒序，取 5 个
```

“是不是 AI 通过的”要看**最近一次**进入已上架的记录：一个活动可能先被 AI 通过，下架后又被运营重新上架。这时它现在的“上架”是人工决定的，不该算 AI 的账。

### 决策 3：详情页的信息

按你选的 A：

- 活动信息（含下架原因）；
- **AI 历次要求修改的理由**：从状态历史里筛出 `AI_REQUEST_REVISION` 的记录；
- 最新一份完整的 AI 报告；
- 完整的状态历史。

**按钮由状态决定**：转人工的活动显示“通过 / 要求修改”；抽检中的显示“没问题 / 有问题，下架”；已上架的显示“下架”；已下架（不是放弃的、没结束的）显示“重新上架”；审核中或需修改的显示“交回 AI 重新审核”。

### 决策 4：并发只靠乐观锁

两个运营同时处理同一个活动：

- 状态变化：D2 的 `@Version` 让后提交的那个人收到 409；
- 抽检：后处理的人找不到“待抽检”的记录，同样返回 409。

前端收到 409 会提示并自动刷新详情，让运营看到别人刚做的决定。

### 决策 5：运营账号由 admin_zero 新建

- 用户名 3～30 位字母、数字或下划线；
- 初始密码用 `SecureRandom` 生成 16 位（去掉了容易混淆的 0/O、1/l/I），**只在创建时返回一次**，数据库只存 BCrypt 哈希；
- 要求 `ROLE_ASSIGN` 权限，只有 admin_zero 有。管理员角色仍然不能通过任何接口授予。

### 决策 6：小红点用状态历史来算，不建通知表

```
红点数 = 这个组织的活动中，在“上次打开我的事件”之后，
        有状态历史记录是 AI 或运营做的 —— 的活动个数
```

用户表加了一个 `events_seen_at` 字段，打开“我的事件”时更新。**状态历史本身就是一份完整的事件流**，红点只是对它的一次计数，不用另外维护一张通知表。代价是只能告诉组织“有几个活动有变化”，不能告诉它“具体发生了什么”。具体内容要进页面看。

**前端的一个竞争问题**：打开“我的事件”时，侧边栏会刷新红点数，页面同时发出“标记已读”。如果刷新请求先发、结果后到，就会把已经清零的数字又改回旧值。解决办法是加一个“代次”计数：每次标记已读，代次加一；刷新请求发出时记下当时的代次，结果回来时代次已经变了，就丢掉这个结果。

### 真实启动（吸取 PROBLEM_LOG 071 的教训）

V34 成功执行，Hibernate 校验通过。然后用脚本把主要接口跑了一遍，22 项全部符合预期：

- admin_zero 登录，新建运营账号，重复的用户名被拒绝；
- 新运营用初始密码登录，角色是 OPERATOR；

**脚本在本地数据库里留下了测试数据**：一个名为 `d3_smoke_` 开头的运营账号，一个 `d3org_` 开头的组织账号和一个已放弃的草稿。

## 五、已知边界与后续

- 两个运营**同时点“抽检”**，可能抽到同一个活动，后一个会因为唯一约束报错（500）。概率很低，没处理。
- 抽检的活动如果在抽检期间被下架或修改，它的抽检记录会一直停在“待处理”，只是不再显示。不影响功能，但数据不够干净。
- 红点只告诉组织“有几个活动有变化”，不告诉“发生了什么”。
- 运营不能修改自己的密码（没有“修改密码”功能，学生和组织也没有）。
- 审核队列没有分页，转人工的活动多了以后要加。

## 六、可迁移的模式

1. **单一入口的回报**：D2 把状态变化收口之后，D3 加一整个后台，没有新增一行改状态的代码。
2. **观察不是状态**：抽检、点赞、收藏这类“对一个对象的记录”，放在旁边的表里，不要塞进对象的状态机。
3. **一个队列，多种来源**：给处理人一个统一的工作入口，来源用标签区分。
4. **从事件流派生计数**：有了状态历史，红点只是一次计数查询，不需要通知表。
5. **一次性密码**：系统生成，只显示一次，只存哈希。

### 面试怎么讲（STAR）

- **S**：AI 审核连续失败后转人工的活动无人处理；运营进不去评测候选页面；没有办法创建运营账号；组织不知道自己的活动被改过。
- **T**：做一个运营后台，复用 D2 的状态机，不新增改状态的逻辑。
- **A**：
  - 审核队列合并“转人工”和“抽检”两种来源，先来先审；
  - 抽检用一张独立的表记录，活动状态不变；
  - 详情页从状态历史里还原 AI 历次的拒绝理由；
  - 运营账号由超级管理员新建，初始密码只显示一次；
  - 组织端红点从状态历史派生，前端用代次解决竞争。
- **R**：运营后台三个模块上线，所有决定仍然只经过 D2 的一个入口；真实启动并跑通了主要接口，越权访问被正确拒绝并记入审计日志。
