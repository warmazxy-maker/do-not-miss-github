## 二、总控 Agent 的想法是怎么来的

我最初的建议是在现有模块上补“目标”“提醒”“引导写心得”等功能。你没有沿着这条路走，而是指出了一个更根本的问题：

> 现在除了教练和刚改的搜索，几乎全是在某个节点调用一下 AI 写个报告、做个计划，没有一个负责实时和用户沟通、监控用户状态的 super master。

你设想的总控：能看到项目的全局功能，管理目标，有自己的记忆和工具集，还能把其他功能当工具调用。

我的评估是：方向对，而且正好补上“记”和“继续”两环；地基已经有一半（画像、教练记忆、Agent 运行记录、限流、导购的“先决定动作再执行”）；缺的是原生工具调用能力和“目标”数据。我补充了一条原则：**总控负责和人打交道，不负责打分**。审核、评分这些流程保持原样，总控只调用它们，否则评分会变成黑箱，B0 打下的评测地基就白做了。

## 四、实验：现在的模型能不能调工具

讨论 F0 之前我查了配置，发现实际用的模型是 `deepseek-v4.1-flash`，走的是第三方中转站，不是阿里云官方接口。中转站对工具调用的支持不一定完整，所以先做实验：给 3 个假工具，5 种场景各试 2 次。

结果 10 次全部正确：能自己提炼参数、能并行调用两个工具、闲聊时不调用工具、能接上工具结果继续回答。结论是直接用原生工具调用，不用退回导购那种“让模型输出 JSON 选动作”的方式。

## 五、F0 的逐题讨论

### 1. 注册表放代码还是放数据库表
我推荐代码作为唯一来源、运维面板只展示。你同意：“没必要存成一个表”。

### 2. 归属关系由谁登记
你原来说的是“工具登记属于哪个 Agent”。我建议反过来，由 Agent 登记白名单，因为一个工具会被多个 Agent 共用。你的回答是：“其实我只是想表示它们的绑定关系而已，你的逻辑比我清楚。”

### 3. 风险等级
你要求做成维度：**数据是否修改 × 会不会调用模型**，并且“最好留出别的维度的设计空间，也许之后还要分别的风险等级”。落地成 `ToolRisk` record：加一个维度就是加一个字段，运维面板自动显示。

### 4. 协议
同意。

### 5. Java 只做结构检查
你表示了解。

### 6. 一轮的上限
你同意了我给的数字，并补充了一个硬性要求：

> 如果工具出错，一定要直接如实说明，但不要搞得特别专业的口吻，否则哪里发生降级我都不知道。

这直接影响了实现：诚实不能只靠提示词，`AgentLoop` 会把每个失败变成一句平常话放进 `notices`，不管模型怎么回答都会显示。实际验证时还真碰到了一次中转站出错，系统如实道歉了。

### 7. 返回结果要不要“瘦身”：你纠正了我
我原来的说法是“比如 50 条历史全塞进去既费钱又让模型糊涂，所以每个工具定义精简版，比如最多 10 条”。你指出这个想法不对：

> 用户查最近的任务，就该全量返回。你说的那种情况更多在于无尽查询，比如用户说想看历史记录，模型问问日期，用户说上个月，那就查上个月。瘦身充其量是把没用的字段、字符做剪枝，而不是语义上削减内容。

落地规则：
- 有边界的数据全量返回；
- 没有边界的数据由参数**强制**带日期范围，学生没说清楚时，模型去问；
- 只裁剪无用字段和特别长的文字；
- 另有一个结构上的安全上限（100 条），触发时必须说明，不能悄悄截断。

这条纠正很重要。按我原来的“最多 10 条”，模型会在不知情的情况下漏掉学生的数据，然后给出错误的结论。
