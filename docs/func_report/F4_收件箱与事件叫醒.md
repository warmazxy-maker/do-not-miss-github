## 一、用大白话说，这次做了什么

Tandem 以前只有你开口它才动，现在平台上发生了值得说的事，它会**主动给你留言**。

- **留在哪**：就留在你和 Tandem 的那条长对话里，标着“主动找你”。导航上 Tandem 旁边会出现红色数字；打开页面时，顶部提示“Tandem 主动给你留了 N 条消息”，同时自动标记为已读。
- **哪些事会叫醒它**：
  - 活动签到成功；
  - 目标的某一步完成（全部完成时，会提议你把目标标为完成）；
  - 能力晋级（包括复核通过后的晋级）；
  - 你预约的活动明天开始；
  - 某个目标超过 7 天没回顾。
- **谁来写**：“活动明天开始”用固定模板写，不调用模型；其他的由 Tandem 写，它也可以判断“不值得说”，一句都不留。
- **防打扰**：
  - 每天最多 3 条，超出的挪到第二天早上 8 点，和那天的第一条合在一起说；
  - 同一件事永远只说一次；
  - 10 分钟内发生的几件事合成一条；
  - 提醒和回顾邀请不在夜里（8 点前）发。
- **你能控制**：Tandem 页右侧栏有“主动留言”设置，可以关掉全部，也可以按 5 个类别分别关掉。
- **留言只说话，不带卡片**：主动留言时不会出确认卡片。你回复之后进入正常对话，需要卡片时再出。
- **回复能接上**：每条主动留言都带一条你看不到的系统备注，写明起因和涉及的活动、目标编号。你回复“这个活动是谁办的？”，它直接按编号去查。

另外按讨论定的：F3 里的“里程碑”在界面和提示词里改名为“**步骤**”，“里程碑”留给能力系统用；F3 里“超过 7 天没回顾就在聊天时顺口问”，改成了由主动留言来邀请。

## 二、整体结构

```
                ┌─────────── 扫描器 WakeScanner（只读其他模块的表，不改现有功能）──────────┐
每 1 分钟：成长记录表里新增的记录 → 活动签到 / 目标的某一步完成
           能力状态表的等级 vs 上次看到的等级 → 能力晋级
每 10 分钟（8 点以后）：明天开始的预约 → 活动提醒；7 天没回顾的目标 → 回顾邀请
                └──── 写进 tandem_wake_triggers（每件事一个去重键，永远只记一次）────┘
                                     │ process_after = 现在 + 10 分钟（合并窗口）
                                     ▼
处理器 WakeProcessor（每 1 分钟）：按学生处理到期的触发
  1. 抢占：PENDING → PROCESSING（比较后再交换），同时把 10 分钟内即将到期的一起拿上（合并）
  2. 过滤：你关掉的类别 → 跳过；情况变了（预约取消了、目标刚回顾过）→ 跳过
  3. 今天已经留了 3 条 → 改到明天 8:00 再处理
  4. 只有提醒 → 固定模板；否则 → 叫醒 Tandem（master_wake：只读工具 + 留言工具，最多 4 轮）
       · 它调用了“留言” → 写进对话；它没调用 → 不留言（如果有提醒，提醒照发）
       · 模型失败 → 5 分钟后重试一次，再失败就放弃
  5. 留言存进 tandem_messages（主动、未读、隐藏备注），触发记为完成并关联这条消息
                                     │
                                     ▼
前端：导航红点（每分钟查一次未读）→ 打开页面 → 提示条 + “主动找你”标签 → 标记已读
下一轮对话：隐藏备注作为系统消息放在这条留言前面 → Tandem 知道你在回应什么
```

## 三、关键决策

1. **主动留言就是对话的一部分**（你的第 1 点，方案 B）。收件箱只负责“未读”这个状态，你在对话里直接回复，Tandem 也记得自己说过什么。
2. **第一批 5 种事件**（第 2 点）。能力里程碑里另外三种（第一次有证据、晋级待复核、加分最多）不叫醒，原因见讨论记录。
3. **提醒用模板，其他用模型**（第 3 点）。模板留言靠隐藏备注让模型“看得到”（你在讨论中提出的问题）。
4. **防打扰**（第 4 点）：每天 3 条，超出的挪到第二天合并；同一件事只说一次；10 分钟合并；Tandem 可以选择不说。
5. **可以关**（第 5 点）：总开关加 5 个类别开关，默认全开。
6. **主动留言不带卡片**（第 6 点）：叫醒用的 Agent 工具列表里根本没有写入工具。
7. **失败重试一次，计数放运维面板**（第 7 点）。

### 实现中我自己定的（需要你知道）

- **用“扫描 + 数据库触发表”，没有用 RabbitMQ 消息。**计划里原本写“由 RabbitMQ 消息触发”。改的原因有三个：
  - 用消息就得在签到、评分这些现有流程里加发消息的代码，违反“现有功能不改”；
  - 10 分钟合并、挪到第二天、失败后重试，这些都需要“延后处理”，用一张带 `process_after` 的表比用消息队列的延迟消息简单得多；
  - 触发表本身就是一份记录，去重、统计、排查都直接查表。

  代价是最多有 1 分钟的延迟，扫描也有一点开销（见第六节）。
- **晋级通过比对检测。**系统里没有“晋级了”这个事件，等级只存在能力状态表里。所以我另存一份“上次看到的等级”，等级比上次高就算晋级。第一次运行和第一次见到的能力只记录、不触发，避免一上线就把历史全说一遍。
- **成长记录用 id 游标。**每次只看比上次大的 id。第一次运行只记录当前位置。
- **留言工具只“打草稿”，由处理器统一写入。**这样留言、隐藏备注和对应的触发是一起保存的，也保证每次叫醒最多留一条。

## 四、验证中发现并修复的问题（PROBLEM_LOG 078）

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| **Tandem 谎称“卡片准备好了，第 9 号”，其实根本没调用工具** | 历史里有很多“卡片准备好了，第 N 号”的旧回答，模型照着样子编了一条，连编号都是编的 | 提示词加硬规则：只有调用了工具、拿到卡片编号，卡片才存在；没调用工具，绝不能说准备好了，也不能编编号。修复后同样的请求真的调用了工具。**页面上不会出现假卡片**，因为卡片是后端真实生成的 |
| Tandem 说“你有 1 个进行中的目标”，其实是 0 个 | 沿用旧回答里的说法，没信系统给的目标列表（和 076 同一类问题） | 提示词加规则：系统给的长期记忆、目标、卡片状态才是现在的真实情况，旧回答可能已经过时。修复后它先查了目标，说对了 |
| 主动留言里说“11/26 那场记得去”，那个预约早就撤销了 | 叫醒用的 Agent 也会看到对话历史，同样的问题 | 叫醒的提示词也加上同一条规则（版本 `tandem-wake-v2`）。**这一条修复后没有再现场复测** |

这三个问题的根源相同：**模型更相信自己在对话里说过的话，而不是系统给的最新数据。**提示词能缓解，但不能根治，要靠 F5 的评测来持续盯住。按你定的原则，这类语义问题不在 Java 里写关键词规则去拦。

## 六、从架构师角度要注意的工程点

1. **轮询扫描 vs 事件驱动。**选扫描是为了“零侵入”和“延后处理”简单，代价是：
   - 延迟最多 1 分钟（对收件箱完全够用）；
   - 能力等级每分钟全表扫一次。现在只有几十行，没问题；等到几万行时，要改成按 `updated_at` 增量扫，或者在评分服务里发事件。

   这是“变更数据捕获”的穷人版。规模大了，标准做法是读数据库的 binlog（比如 Debezium）。
2. **去重键决定“只说一次”的语义。**
   - 签到按活动 id；晋级按“能力 + 等级”（掉级后再升回同一级不会再说，这是有意的）；
   - 提醒按“预约 + 日期”；
   - 回顾按“这段沉默从什么时候开始”：回顾一次后开始新的一段，才会再邀请。

   去重键怎么设计，就决定了产品行为，以后加新的事件类型时要先想清楚。
3. **处理器是单线程、一个学生一个学生地处理。**每次叫醒最长 90 秒（模型），学生多了会排队。将来可以：多个工作线程，用“比较后再交换”抢占（已经实现，多实例也安全）；或者给叫醒单独一个模型额度。
4. **后台的模型成本没有限流。**每个学生每天最多 3 条留言，所以上限可控；但模型失败重试、或者 Tandem 选择不说，都不占这 3 条，极端情况下一个学生一天可能叫醒很多次。将来要加一个“每个学生每天最多叫醒 N 次”的硬上限。
5. **最终一致和时间窗口。**从扫描到发出，中间有 10 分钟合并窗口，再加上处理时的“情况变了”检查（预约取消、刚回顾过），保证不会说过时的事。但从“检查”到“写入”之间还有几秒的窗口，属于可以接受的最终一致。
6. **隐藏备注是让模板消息变成“上下文”的关键。**备注里放编号（活动、预约、目标），而不是只放文字，模型才能直接调用工具。以后任何“系统替 Agent 说的话”都应该带这种结构化的备注。
7. **时区。**
   - 数据库里 `Instant` 存的是 UTC，`LocalDateTime`（活动时间）存的是东京时间；
   - 扫描“明天”用活动表的本地时间，“每天上限”和“挪到明天 8 点”用东京时区换算。

   验收时用 SQL 改时间也要注意这一点，我是用相对时间（往前拨 11 分钟）避开的。将来部署到别的时区，要确认 `app.mcp.default-timezone`。
8. **Agent 的“不相信系统数据”是这个方向最大的风险**（076、078 反复出现）。对话越长，旧回答越多，问题越容易出现。能做的有：
   - 在 F5 的评测里专门测；
   - 摘要压缩时，把“状态类结论”剔除掉；
   - 将来考虑把旧回答里涉及状态的句子标成“过去时”。
