# B0：推荐评测地基（冻结语料 + 版本化评测集 + 端到端评测）

> 一句话：原来的推荐评测集引用的 30 个活动全部过期，评测已经失效。现在把评测要用的活动连同质量报告**冻结成一份带版本号的文件**，评测时走**专用索引**、使用**固定时钟**和**中性画像**，所以今天跑和下个月跑，结果可以直接比较。另外新增了**端到端评测**：不只测召回出来的候选，还测大模型重排之后学生真正看到的推荐。
>
> **状态（2026-10-24）**：已实现，Maven 全量 153 个测试通过（新增 10 个），后端启动正常。**按约定没有跑真实评测**，评测索引会在第一次运行时自动建立。

---

## 1. 问题：为什么说“尺子坏了”

| 现象 | 原因 |
| --- | --- |
| 评测集引用的活动 #27～#56 全部 `expired=1` | 活动到了结束时间，定时任务就把它标记为过期，并从搜索索引里删掉 |
| 现在跑评测，这 30 个活动几乎一定召回不到 | 召回只查询线上索引，再过滤掉过期的活动 |
| 换一个人跑评测，结果也会不同 | 评测用的是运行者自己的画像 |

本质原因：**评测依赖了会变化的线上状态**，包括活动表、搜索索引、当前时间和用户画像。评测的第一原则是可复现，同样的输入必须得到可比较的输出。

---

## 2. 架构：在召回层引入“语料”抽象

```mermaid
flowchart TB
    subgraph 召回与打分（同一套代码）
        H[HybridEventRetrievalService.retrieve]
    end
    H -->|EventCorpus 接口| L[LiveEventCorpus<br/>MySQL + 线上索引 do_not_miss_events<br/>检索前先处理过期活动]
    H -->|EventCorpus 接口| F[FrozenEventCorpus<br/>events-v1.json 读入内存<br/>专用索引 do_not_miss_eval_events_v1_指纹<br/>不做任何过期处理]
    A[线上推荐 AiService] --> H
    E[评测 RetrievalEvalService] --> H
    E --> R[AiService.rankForEvaluation<br/>与线上同一套重排逻辑]
```

`EventCorpus` 只定义了召回过程中**和数据来源有关**的 5 个动作：BM25 检索、向量检索、按 ID 查找活动、按条件过滤（搜索引擎无结果时的兜底），以及检索前的准备工作（线上用来处理过期活动，冻结语料什么也不做）。

**为什么这样设计**：召回和打分逻辑（RRF 融合、分数归一、过期判断、证据生成）只有一份，线上和评测共用。如果为了评测另写一套召回，评测测到的就不是线上真正在跑的代码，那样的评测是自欺欺人。这就是**依赖倒置**：上层逻辑依赖接口，具体的数据来源从外部传进来。线上通过 Spring 注入 `LiveEventCorpus`，评测则手动传入 `FrozenEventCorpus`。

## 3. 关键设计决策

### D1：冻结什么？活动本身和质量报告一起冻结

**问题**：活动的检索文本由“活动字段 + 质量报告”拼成，大模型重排时也会读质量报告。如果只冻结活动，质量报告重新分析后，评测结果还是会悄悄变化。

**选择**：`events-v1.json` 一共冻结了 55 个活动（数据库中 id≤56 且审核通过的活动），其中 30 个是评测集里标注过的，另外 25 个作为干扰项。每个活动都带上冻结时的质量报告。我昨天发布的测试活动 #58 不在其中。

**代价**：这份文件约 78 KB，可读性尚可。以后如果加入新活动，就要发布 `events-v2`。

### D2：版本号分两层：评测集版本 + 语料版本

`retrieval-eval-set.json` 现在的结构如下：

```json
{
  "version": "retrieval-eval-v1",      // 用例或标注变了就升级
  "corpusVersion": "events-v1",        // 标注针对的是哪份冻结语料
  "asOf": "2026-04-28T09:00:00+09:00", // 评测时钟
  "labelStatus": "INHERITED_FROM_V0",
  "changelog": [ ... ],
  "cases": [ ... ]
}
```

**为什么分两层**：用例和语料的变化频率不同。新增几条差评用例（B4 会做）只需要升级评测集版本；新增活动则要升级语料版本，而且所有标注都可能需要复核。每次评测的返回结果都带一个 `run` 头：模式、评测集版本、语料版本、语料指纹、语料规模、评测时钟和模型。**只有这些都相同的两次结果才能直接比较。**

### D3：语料指纹 = SHA-256(语料文件 + 向量模型名)

**问题**：评测索引里存的是向量。如果有人修改了语料文件，或者换了向量模型，旧索引里的向量就过时了，但系统不会报错，只会悄悄给出错误的结果。

**选择**：把指纹写进索引名，例如 `do_not_miss_eval_events_v1_3fa9c2d1`。只要文件改了一个字节，或者换了向量模型，索引名就会变，系统找不到同名索引，就会自动重建。这是**内容寻址**的思路：名字由内容决定，内容一变名字就变，从根本上避免读到旧缓存。Docker 镜像层、Git 对象用的也是同样的办法。

### D4：固定时钟 `asOf`

**问题**：召回会判断活动是否已结束（已结束的分数清零），重排的提示词里也带有“当前时间”。如果用真实时间，活动迟早都会过期，评测结果也会随时间漂移。

**选择**：评测时把时间工具的返回值替换成 `asOf`，取最早一个活动开始时间的前一天，确保所有冻结活动在评测时都还没结束。有一个测试专门检查“`asOf` 早于每个冻结活动的结束时间”。如果以后有人把 `asOf` 改晚了，这个测试会直接失败。

### D5：中性画像

评测时不读运行者的画像，而是传入一个空画像。否则管理员自己的成长记录会影响排序，换个人跑，分数就不一样。代价是评测测不到个性化效果。等 B3 让反馈影响画像之后，再给用例加上“指定画像”这个字段。

### D6：端到端评测复用线上的重排代码

**问题**：原来的评测只测召回，但学生看到的是大模型重排之后的前 5 个。召回做得好，重排也可能把顺序排坏，反过来也一样。

**选择**：把 `AiService` 里的重排逻辑拆成两层：
- 线上入口的签名不变，内部调用一个能注入两样东西的版本：**质量报告从哪里取**（线上查数据库，评测查冻结文件），以及**模型原始返回的活动 ID**（用来统计幻觉）。
- 新增 `rankForEvaluation(...)` 方法，它使用同一份提示词、同一套校验、同一个自我检查步骤和规则兜底，只是不记录 Agent 运行，也不写会话状态。

### D7：新增四个指标

| 指标 | 含义 | 为什么需要 |
| --- | --- | --- |
| 零结果率 | 学生什么都看不到的用例占比 | 推荐“空手而归”的体验最差 |
| 过期混入率 | 返回结果中已结束活动的占比 | 正常应该是 0；不为 0 说明时钟或过期过滤出了问题，这是一个自检指标 |
| 模型编造 ID 率 | 模型返回的活动 ID 中，不在候选里的占比 | 校验层会把这些 ID 过滤掉，所以用户看不到，但这能衡量模型有多不守规矩，也能看出换模型后是变好还是变差 |
| 规则兜底率 | 模型不可用或返回为空、最后改用规则排序的用例占比 | 兜底比例高时，端到端分数反映的其实是规则的效果，不是模型的效果 |

原有的 NDCG@5、MRR、命中率、精确率、召回率保留不变，计算方式也没变（收益 2^相关度 − 1，按 log2(名次+1) 折损）。端到端结果会同时给出“召回阶段的 NDCG”和“重排之后的 NDCG”，两者一比就知道重排是加分还是减分。

### D8：评测接口改为仅限运维管理员，顺手补上了一个安全漏洞

- 评测每条用例都要调用模型（查询改写，端到端模式还要再调一次重排），30 条用例就是 30～60 次调用。这属于运维操作，所以和运维面板用同一套权限。
- 排查时发现，`POST /api/ai/retrieval/reindex` **原先没有任何鉴权**：任何人都能触发全量重建索引，而重建期间线上检索会降级。现在同样只对运维管理员开放。部署文档里已经加了说明。

## 4. 一次端到端评测的请求路径

1. `GET /api/ai/retrieval/evaluation/end-to-end`：先检查运维权限。
2. `RetrievalEvalFixtures` 读取评测集和语料，计算指纹。评测索引不存在时，用冻结活动重建索引（只会在第一次运行时发生，每个活动要做一次向量化）。
3. 对每条用例：
   - 用中性画像和固定时钟，在冻结语料上召回前 15 个候选（和线上一样是 15 个）；
   - 计算召回阶段的 NDCG@5；
   - `rankForEvaluation` 用同一套线上重排逻辑得到前 5 名，同时记录模型的原始 ID；
   - 计算重排后的 NDCG@5 和 MRR，并找出模型编造的 ID。
4. 汇总后返回 `run` 头、汇总指标和逐条结果。

## 5. 测试与未覆盖部分

**新增或改写的 10 个测试**：
- 评测集带版本号，30 条用例、80 个标注的结构完整。
- **所有被标注的活动都在冻结语料里**（防止有人删了活动，标注却指向不存在的 ID）。
- **评测时钟早于所有冻结活动的结束时间**。
- 指纹在内容相同时稳定，换向量模型就会变化；评测索引名不会和线上索引重名。
- 质量报告随冻结语料一起读入，JSON 数组字段正确转成文本。
- 多级相关度下 NDCG、MRR、精确率和召回率的计算（手算出 NDCG = 0.71 作为对照）；只统计前 K 名。
- 零结果率和过期混入率（时钟拨到活动 1 结束之后，混入率变成 1.0）。
- 冻结语料的过滤语义和数据库一致。
- **在冻结语料上召回完全不碰数据库**：测试里把线上语料设成 null，只要碰到就会直接报错。

**没有覆盖的**：
- **没有运行真实评测**（按约定），所以还没有基线数字。第一次运行时要留意：评测索引的构建和 30 次查询改写都要消耗模型额度。
- 端到端评测没有像能力标签评测那样做录制回放，现在只有 LIVE 模式，每次结果会有小幅波动，应该比较平均值，不要盯单条。
- 评测集的标注还是旧版本继承下来的（`INHERITED_FROM_V0`），没有重新审核过。

## 6. 可迁移的模式

1. **评测先求可复现**：把所有会漂移的输入（数据、时间、身份、索引）都固定下来，剩下唯一的变量就是被测的代码或模型。
2. **用接口隔开数据来源，不要复制业务逻辑**：评测走的必须是线上同一条代码路径。
3. **内容寻址的缓存**：名字由内容的哈希决定，内容一变就自动失效，不用记得手动清缓存。
4. **把不变量写成测试**：例如“所有标注 ID 都在语料里”“时钟早于所有结束时间”。这些规则平时不会有人记得检查，测试替人记着。
5. **输出带上元数据**：结果自带版本和指纹，防止把不可比的两次结果拿来比较。

## 7. STAR

- **S**：推荐评测集引用的活动全部过期，评测实际上已经失效，而且结果还受运行时间和运行者画像影响；评测只测召回，不测学生最终看到的推荐。
- **T**：建立可复现、带版本的推荐评测，覆盖召回和重排两段，为后续的反馈闭环提供度量手段。
- **A**：引入 `EventCorpus` 抽象，让线上和评测共用一套召回代码；冻结 55 个活动及其质量报告；评测集和语料分别加版本号；用 SHA-256 指纹命名评测索引；固定时钟、使用中性画像；把重排拆出可注入的版本，用来做端到端评测；新增零结果率、过期混入率、模型编造 ID 率和规则兜底率；评测和重建索引接口改为仅限运维管理员，补上了重建接口未鉴权的漏洞。
- **R**：评测从“必然接近 0 分”变成可复现、可比较；新增 10 个测试，全量 153 个通过；线上代码路径的行为不变。
