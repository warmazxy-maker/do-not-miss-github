## 一、用大白话说，这次做了什么

以前，学生说的“我想练口语”只是一句话：推荐完活动就没了。现在它可以变成一个**目标**，一直留着，Tandem 每轮对话都能看到。

- **一个目标包括**：你用自己的话写的一句目标、怎样算达成、类型（结果型 / 能力型 / 习惯型）、可选的目标日期。
- **目标由什么组成**：1～8 个按顺序排好的**里程碑**。每个里程碑都是平台上的一件事：一个活动，或一个挑战。自学、练习这类找不到对应活动的步骤，用新挑战来承载。
- **进度是自动算的**：活动签到成功、挑战完成，这一步就算完成。不能手动打勾，Tandem 也不能。
- **成长展示**：完成的里程碑给哪些能力桶带来了证据，就在目标下面显示出来，比如“带来成长：日语”。
- **怎么建目标**：Tandem 按目标类型去搜活动，挑出合适的排好顺序，没有活动的步骤配上新挑战，然后出**一张卡片**，你一次确认。这就是你说的“比原先的规划 Agent 强”的那部分。
- **怎么改**：通过 Tandem 改目标、完成、放弃都走卡片，可以撤销。你也可以直接在面板上完成、放弃、重新开始、去掉某一步，不需要卡片。
- **最多 3 个**进行中的目标。超过 7 天没回顾的目标，Tandem 会在聊天时顺口问一句，只问一次。

## 二、整体结构

```
Tandem 每轮的上下文：长期记忆 + 【学生的目标】（进行中的目标、每一步的状态、带来的能力、该不该回顾）
        │
        ▼
"我想年底前练好口语" → 搜活动 ×2（按能力型：先入门、再进阶）→ 查挑战 → 建目标（卡片）
        │
        ▼ 你点确认（F2 的事务和状态机）
TandemGoalService.create：新挑战通过现有的挑战服务创建 → 存目标 → 存里程碑
        │
        ▼
面板 / Tandem 每次读取时，从平台推出每一步的状态：
  活动：预约记录是“已完成”→ 已参加；“预约中”→ 已预约（活动已结束就是“没有签到”）；没预约 → 还没预约
  挑战：已完成 → 完成；进行中 → 进行中；已取消 / 不存在 → 不可用
成长：已完成的那些步 → 能力证据（来源 = 活动或挑战 id，状态 = 已评分）→ 能力桶名称
```

## 三、关键决策

1. **目标是新的实体**（你的第 1 点）。类型只是其中一个字段，它的作用写在提示词里：
   - 结果型：找直接相关的备考、求职、实战类活动，按时间往目标日期排；
   - 能力型：找能反复练、有真人互动和反馈的活动，由浅到深；
   - 习惯型：找时间固定的活动，再配一个打卡挑战。
2. **能力桶不是输入，只用来展示**（第 2 点）。目标不挂能力桶，推荐也不读能力桶；完成的里程碑产生了哪些能力证据，就在目标下展示哪些能力。
3. **里程碑只能是平台上的事**（第 3 点）。这是我对“挂在平台事物吧”的理解：不存在纯文字的里程碑，自学步骤用挑战来承载。好处是进度永远是真实发生的事，不靠自觉打勾。代价是线下自己完成、没有在平台签到的事不会被计入（见第七节）。
4. **完成、放弃只由你决定**（第 4 点）。Tandem 只能在里程碑都完成、或者目标明显不适用时提议，你同意了才出卡片；系统永远不会自动改目标状态。
5. **最多 3 个进行中**（第 5 点）。出卡片时检查一遍，确认时再检查一遍，“重新开始”也受这个限制。
6. **一张卡片建一整个目标**（第 6 点），撤销时整体撤销：目标、里程碑和这张卡片新建的挑战一起删掉。
7. **你可以直接操作，不需要卡片**（第 7 点）：完成、放弃、重新开始、去掉某一步、删除目标。删除目标不会删挑战，挑战已经是你的了。
8. **回顾**（第 8 点）：每轮都给 Tandem 看目标；超过 7 天没回顾，会在上下文里提醒它问一句。F4 再改成主动发消息到收件箱。
9. **面板放在右侧栏**（第 9 点，方案 A）。
10. **过去的目标**（第 10 点）：保留最近 5 个，可以重新开始或删除；Tandem 也能看到。

### 撤销用的“快照”

和 F2 一样，撤销前会比对快照：目标的文字、类型、日期、状态和里程碑列表（按内容比，不按编号比）。和执行完时一模一样才撤销，否则拒绝。

- “改目标”在确认时也会比对：如果出卡片之后你在面板上改过这个目标，确认就失败。
- 一起新建的挑战，只要完成过、取消过、改过，或者被排进了日程，整个撤销就会被拒绝。也就是说，撤销要么全部成功，要么什么都不变，不会只撤一半。

## 四、验证中发现并修复的问题

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| **所有目标的撤销都被误拒，“改目标”的确认也会每次失败**（PROBLEM_LOG 077） | 快照里有数字编号。现场生成的快照里是“长整数”节点，存进数据库再读出来变成“整数”节点，Jackson 认为两者不相等 | 比较前两边都先转成文字再读回来。补了一个“存进去再读出来”的单测；F2 的快照里只有文字和时间，不受影响 |
| 建目标卡片上的“去看看”链接指向当前页 | 链接写成了 Tandem 页 | 目标卡片不显示链接，面板就在旁边 |

## 六、从架构师角度要注意的工程点

1. **派生状态，而不是同步状态。**里程碑完成没有用消息队列去“打勾”，而是每次读取时从预约和挑战的状态推出来。好处是永远不会不一致，签到、撤销、取消都自动反映，不需要写任何同步代码。代价是每个里程碑每次读都要查几次数据库：现在最多 3×8 步，问题不大。将来目标多了或者 F4 要批量扫描，可以加批量查询或缓存。这是“读时计算”和“写时物化”的经典取舍。
2. **快照比较要和序列化无关**（077 的教训）。凡是“存一份 JSON，以后拿来比”的地方，都要把两边规整成同一种形式再比较。F2 侥幸没有数字字段才没踩到。以后新写的回滚工具，要么复用 `matches` 这种比较，要么快照里只放文字。
3. **组合写操作的回滚要整体成功或整体失败。**建目标一次会动三类数据（目标、里程碑、新挑战），所以回滚必须在同一个事务里，任何一部分不能回滚就整个拒绝。如果哪天其中一部分换成异步服务，就得改成“补偿”模式。
4. **两种写入路径共存。**同一个目标既能由 Tandem（经过卡片）改，也能由你直接改。快照守卫正好保证两者不会互相覆盖：你改过，Tandem 的旧卡片就不能执行、也不能撤销。这个模式以后可以推广到所有“人和 Agent 共同编辑”的数据上。
5. **上下文预算。**目标上下文每轮都会注入，3 个目标、每个 8 步、每步一行，最多大约 30 行。现在没问题；到 F4 收件箱和更多工具加进来以后，要注意总的上下文长度（可以给目标上下文只放摘要，细节让 Tandem 用“查目标”去取）。
6. **一轮的时间预算越来越紧。**建目标要搜好几次活动，这次用了约 80 秒，上限是 90 秒。搜活动本身要 30 秒以上，是瓶颈。选项包括：放宽上限；让多个搜索并行（现在已经是并行的）；或者给“建目标”这类重任务单独的预算。先观察，F5 的耗时统计出来后再决定。
7. **模型会混淆“卡片编号”和“目标编号”。**验收时 Tandem 说“目标第 6 号”，6 其实是卡片编号，目标编号是 1。不影响执行（工具参数是对的），但说法会让人困惑。以后可以在上下文里把两种编号写得更不一样（比如目标用“G1”）。
8. **成长展示依赖异步评分。**挑战完成后，能力证据要等后台评分跑完才出现。所以面板上“带来成长”会晚几十秒出现，这是正常的。

## 七、你来验收

1. 跟 Tandem 说一个你真实想达成的事，看它找的活动、排的顺序、配的挑战合不合理。
2. 确认后看右侧栏的面板；预约其中的活动，看那一步变成“已预约”。
3. 在面板上试试完成、放弃、重新开始、去掉一步。
4. 想一想第三节第 3 条的取舍是否可以接受：“里程碑只能是平台上的事”，意味着线下自己做了、但没在平台签到的事不会被计入进度。
