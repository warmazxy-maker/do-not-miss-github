## 现状摸底（2026-10-26）

| # | 发现 | 严重程度 | 处理 |
|---|---|---|---|
| 1 | 后端完全不检查角色，只靠前端路由区分学生端和社会端 | 高 | D1 |
| 2 | 审核通过 / 驳回、重新分析的接口没有鉴权，匿名也能调用 | 很高 | **D0 已修** |

## 顺序

```
D0 安全止血 → D1 权限模型 → D2 活动生命周期状态机 → D3 运营审核后台 → D4 限流与配额
```

D2 的每一步都要回答“谁可以做”，所以依赖 D1；D3 是 D2 的操作界面；D4 相对独立，但其中的“豁免”规则依赖 D1。

## D1：权限模型（已完成，2026-10-26）

> 决定：五个角色（学生、组织、运营、管理员、超级管理员 ADMIN_ZERO），一人一个角色，新增角色只需加数据；权限挂在角色上；自己写注解 + AOP 统一校验；admin_zero 由后台指定，暂不开放授予管理员的接口；组织可以有多个账号，成员关系先记录、不验证（**设计缺口**）；没加注解的接口先放行；审计日志要记；保留运维总开关。详见 `func_report/D1_权限模型.md`。


**全局**
1. 【你定】需要哪些角色？学生、组织、管理员、运营？管理员和运营要不要分开？一个人能不能同时有多个角色？
2. 【讨论】权限挂在角色上（权限 → 角色 → 用户），还是在代码里直接判断“是不是管理员”？建议做“权限 → 角色”这一层，但规模要小：权限用代码枚举定义，不做在后台自由配置权限。
3. 【讨论】用 Spring Security，还是自己写一个注解加拦截器？建议用自己写的方式：原理和代理、AOP 相同，也方便以后迁移到 Spring Security。

**局部**

4. 【你定】第一个管理员怎么产生？种子账号、启动参数，还是由已有管理员授予？
5. 【讨论】组织归属：是否限制组织账号只能以自己所属组织的名义发布活动？
6. 【了解】默认拒绝：没有标注权限的接口，默认是放行还是拒绝？
7. 【讨论】管理员操作要不要记审计日志？
8. 【了解】运维白名单迁移到“管理员角色”；环境变量开关是否保留？

## D2：活动生命周期状态机（已完成，2026-10-28）

> 决定：要“已保存”草稿，取消“已拒绝”（保留枚举备用），不合格一律“需修改”；“已结束”走时间维度，按时间推算，再由定时任务通过状态机把活动转成“已下架（活动已结束）”；AI 直接决定，连续三次要求修改后转人工；修改已上架的活动要重新走 AI 审核，期间学生看到“已下架：活动重新上架审核中”；下架必须填原因，组织只能下架，重新上架只有运营能做；下架或结束不取消预约，在预约页醒目提示；签到改由组织扫码；手写状态机，不引入框架。详见 `func_report/D2_活动生命周期状态机.md`。

**全局**
1. 【你定】活动有哪些状态？要不要“草稿”？“已拒绝”和“需修改”的区别是什么？已拒绝的活动能不能重新提交？
2. 【讨论】“已结束”是状态机里的一个状态，还是根据时间推算出来的属性？
3. 【你定】AI 质量审核有多大权力？直接决定、只给建议，还是按置信度分流（高置信自动处理，低置信转人工）？

**局部**

4. 【你定】已通过的活动被修改后，要不要重新审核？改哪些字段才需要重新审核？
5. 【讨论】删除改成“下架”（软删除）吗？已经有人预约的活动被下架，怎么处理？
6. 【了解】副作用（写入或删除搜索索引、发通知）统一绑定在状态变化上。
7. 【了解】并发问题：用乐观锁（版本号）防止两个人同时操作同一个活动。
8. 【讨论】签到是否改成必须由组织扫学生的码？

## D4：限流与配额

**全局**
1. 【你定】首先要防的是什么：恶意刷接口、成本失控，还是服务被压垮？
2. 【讨论】按什么维度限：用户、IP、接口，还是全局？没登录的接口（登录、注册）怎么办？要不要防暴力破解？

**局部**

3. 【你定】具体数值。我会先给一版建议。
4. 【讨论】算法：固定窗口、滑动窗口还是令牌桶，都用 Redis 实现。

8. 【了解】运维面板上显示被限流的次数和对象。
