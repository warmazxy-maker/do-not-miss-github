# 手动测试手册（Stage 12.1 ～ 17 真实环境验收）

> 目标：在真实的 MySQL、RabbitMQ 和大模型环境下，把最近做的功能都亲手走一遍。
> 用到的工具只有三个：**Docker Desktop 窗口**、**两个终端窗口**、**浏览器**。
> 预计耗时：45～60 分钟。其中 AI 处理需要等待，每次完成活动后要等 1～3 分钟。

按顺序做，每一步都有“应该看到什么”。看到的和写的不一样，就记下来告诉我。

---

## 第 0 步：开始之前（建议先做）

**备份数据库。** 这次启动会执行 3 个新的数据库迁移（V26、V27、V28），第 5 步还会改一点测试数据。备份之后就不用担心了。

在 Docker Desktop 中打开 `do-not-miss-mysql` 容器的 **Exec** 标签页（打开方法见附录 A），粘贴下面这行：

```
mysqldump -udonotmiss -pdonotmiss123 do_not_miss > /tmp/backup-before-test.sql && ls -lh /tmp/backup-before-test.sql
```

应该看到一行文件信息，文件大小不是 0。

## 第 1 步：启动依赖服务（Docker Desktop）

1. 打开 **Docker Desktop**，等左下角显示 Engine running。
2. 左侧点 **Containers**，确认这三个容器是绿色的 Running 状态：
   - `do-not-miss-mysql`

3. 如果是灰色的，点右边的 ▶ 启动。如果列表里根本没有这些容器，在 `do-not-miss-backend` 文件夹里打开终端，执行一次：

```bash
docker compose up -d
```

`do-not-miss-opensearch` 是可选的，没启动也不影响这次测试。

如果看到 `Capability V2 scoring deferred because the model is unavailable`，说明大模型暂时连不上，系统会在 1 分钟后自动重试。这是正常的保护机制，继续等就行。

### 4.6 （可选）在数据库里核对

用附录 A 的方法进入 MySQL，粘贴：

```sql
SELECT id, run_type, status, LEFT(goal, 40) AS goal FROM agent_runs
WHERE run_type = 'CAPABILITY_V2_PIPELINE' ORDER BY id DESC LIMIT 3;
```

- [ ] 最新一条的 `status` 是 `SUCCEEDED`。

把上面查到的 id 代入下面的 `<runId>`：

```sql
SELECT sequence_no, step_name, status, LEFT(output_summary, 80) AS output
FROM agent_run_steps WHERE run_id = <runId> ORDER BY sequence_no;
```

- [ ] 一共有 6 个步骤：EVIDENCE_SNAPSHOT → KNOWLEDGE_NORMALIZATION → FUNCTION_CANDIDATE_RECALL → FUNCTION_DELIVERY_GATE → FUNCTION_ATTRIBUTION → CAPABILITY_V2_WRITE，全部是 `SUCCEEDED`；
- [ ] FUNCTION_CANDIDATE_RECALL 那一行的输出以 `mode=hybrid` 开头。如果是 `keyword-only`，说明向量服务没连上，召回退回了纯关键词。

```sql
SELECT 'evidence' AS t, COUNT(*) FROM capability_v2_evidence_links WHERE agent_run_id = <runId>
UNION ALL SELECT 'score_audit', COUNT(*) FROM capability_v2_score_audits WHERE agent_run_id = <runId>
UNION ALL SELECT 'class_audit', COUNT(*) FROM capability_v2_classification_audits WHERE agent_run_id = <runId>;
```

- [ ] 三个数字都大于 0：evidence 和 score_audit 的数量相同，class_audit 是 2（知识一条、职能一条）。

## 第 5 步：晋级复核测试（测 Stage 15.1）

正常使用中，要攒很多次经历，分数才会超过 30 分并触发晋级复核。为了测试，这里**手动改一条测试数据**，把一个标签设成“分数够了、阶段还没升”的状态。第 0 步已经做过备份，可以放心改。

### 5.1 构造“卡住晋级”的标签

进入 MySQL（附录 A），先查出你在第 4 步得到的标签：

```sql
SELECT s.id, b.display_name, b.bucket_type, s.ability_score, s.rank_name
FROM user_capability_v2_states s JOIN capability_v2_buckets b ON b.id = s.bucket_id
WHERE s.user_id = 'demo-student' ORDER BY s.id DESC LIMIT 5;
```

选一个知识标签（比如 Spring Boot），把它的 `id` 代入下面的 `<stateId>`：

```sql
UPDATE user_capability_v2_states SET ability_score = 35, rank_name = 'FOUNDATION' WHERE id = <stateId>;
```

### 5.2 在页面上检查

刷新 **个人成就**：

- [ ] 这个标签上出现了 **黄色的 ! 小圆点**；
- [ ] 点开后，抽屉顶部出现黄色横幅：“分数已经够「成长中」了，阶段还停在「基础」”；
- [ ] 横幅右边有 **“补充说明”** 按钮。

> 说明：因为是手动改的分数，不是真实证据推上去的，所以抽屉里可能没有标黄的“卡住晋级”证据卡片，对账提示也可能变成黄色。这都是改数据造成的，属于正常现象。

### 5.3 补充说明

1. 点 **补充说明**，等待 AI 出题，大约 10～30 秒。
2. **检查题目**：
   - [ ] 一共 3 道题；
   - [ ] 前两道标着“你的经历”，题目里提到了你写的那段经历（报名系统、重复报名等）；
   - [ ] 第三道标着“相关延伸”。
3. **认真作答**，每道题写两三句真实、具体的内容，然后提交。
4. **检查结果**：
   - [ ] 如果显示“复核通过，已晋级「成长中」”：关掉弹窗，标签上的 ! 消失了；抽屉里出现“复核通过，晋级「成长中」”的里程碑；补充说明记录里有一条“通过”；
   - [ ] 如果显示没通过：这也是一种正常结果。按钮会变成冷却提示“补充一段新的经历，或在 X 之后可以再试”。
5. （可选）再挑一个标签，重复 5.1 的改数据，这次**随便写几个字敷衍作答**：
   - [ ] 应该显示“这次还没有通过”；
   - [ ] 阶段不变。

## 第 7 步（可选）：模型故障时的延迟重投（测 Stage 17）

这一步要改配置、重启后端，比较麻烦，有时间再做。

1. 用记事本打开 `do-not-miss-backend\.env`，**复制一份备份**，然后把 `AI_BASE_URL=` 后面改成一个错误的地址，比如 `https://invalid.example.com/v1`。
2. 在终端窗口 1 按 `Ctrl + C` 停掉后端，再执行一次 `mvn spring-boot:run`。
3. 新建并完成一个挑战，等 1 分钟，看日志：
   - [ ] 出现 `Capability V2 scoring deferred because the model is unavailable ... deferral=1/8`。
4. 在 MySQL 中查看：

```sql
SELECT id, status, attempts, next_attempt_at, LEFT(payload_json, 60) AS payload
FROM domain_event_outbox WHERE routing_key = 'capability-v2.score' ORDER BY id DESC LIMIT 3;
```

   - [ ] 最新一条的 `next_attempt_at` 是**几分钟之后**的时间，说明延迟重投已经排上了。

5. **把 `.env` 改回原来的内容**，停掉后端再重新启动。
6. 等几分钟（最长等到上一步看到的 `next_attempt_at`）：
   - [ ] 日志出现 `Processed capability V2 scoring message`；
   - [ ] 这个挑战产生的标签出现在个人成就页里，说明**分数没有丢**。

## 附录 B：常见问题

| 现象 | 处理 |
| --- | --- |
| 后端启动时报连不上 MySQL 或 RabbitMQ | 回到第 1 步，确认三个容器都是 Running |
| 完成挑战 5 分钟后，个人成就页还是空的 | 看终端窗口 1 有没有报错；RabbitMQ 管理页 http://localhost:15672（账号 donotmiss / donotmiss123）的 Queues 里，看 `do-not-miss.capability-v2-scoring` 队列有没有积压 |
| 日志一直显示 `keyword-only` | 向量服务连不上，系统已经自动退回关键词召回。功能仍然可用，只是召回质量会差一些；检查 `.env` 里的 `AI_EMBEDDING_*` 配置 |
| 补充说明一直在转圈 | 大模型响应慢，最多等 60 秒；超时会提示错误，可以再点一次 |
