## 开发原则

- 不直接删除旧能力数据，先做兼容与双写，稳定后再考虑下线旧展示。
- LLM 负责事实抽取、标签归一、证据解释，不直接决定最终能力分。
- Java 评分引擎继续负责确定性算分，保证同一套分数标准可解释、可复现。
- 职能桶优先来自稳定种子库，不让 LLM 随便发明岗位职能。
- 知识与技术优先归入稳定粗桶，避免碎片化标签膨胀；细节进入 evidenceFindings 和里程碑。
- 新知识桶创建要严格：必须不存在语义接近桶，且该概念未来具备长期累计价值。
- 所有异步链路都要保留 trace、幂等键、失败重试入口，方便后续定位 bad case。

核心规则：不要把课程知识点、API 名、单个设计技巧直接变成前台标签。它们应写入证据点。例如：

- Java 集合、面向对象、异常处理 -> Java
- Controller、Service、Repository、Spring 事务 -> Spring Boot
- 联合索引、事务隔离级别、唯一约束 -> MySQL
- Outbox、异步投递、重复消费处理 -> 消息队列 / 数据一致性相关桶，按上下文选择

人工验收：用 10 条活动样例检查知识桶是否过碎、过泛、乱合并。

完成情况：新增 `KnowledgeBucketNormalizationAgent`。LLM 只能执行 `REUSE`、`CREATE`、`SKIP` 三种动作：复用时必须引用当前用户已有标签的真实 `bucketId`；新建时 Java 会过滤“能力、技术、学习、项目”等泛名以及“Java 集合入门”、课程名、API 名等过细名称。一个证据最多归入 3 个知识桶；数据库以 `(bucket_type, owner_user_id, normalized_name)` 唯一约束保证同一用户内不重复创建。模型不可用时不新增、不臆测复用，保守地留下待处理结果。

### Stage 09：核心职能候选召回

根据证据内容从职能桶中召回 Top 8 到 Top 12 个候选职能。

目标：LLM 只在候选里选择或拒绝，不自由发明职能。

完成情况：新增 `FunctionBucketCandidateService`。它读取全局 `FUNCTION + __GLOBAL__ + ACTIVE` 的 372 个种子桶，并按标题、描述、复盘、事实点、桶名、别名和职能说明做本地确定性排序，默认返回 Top 10。候选带有 `retrievalConfidence`、原始分和命中短语，供审计与后续 Trace 使用。模糊匹配要求至少 3 个连续字符，避免“服务端”因为共享“服务”而误召回“志愿服务”。

### Stage 10：核心职能归因 Agent

判断一次经历是否真的能提升某个职能。课程学习类经历一般偏知识标签，项目实践、实习、组织活动才更容易提升职能。

人工验收：确认“看课学 Java”不会强行涨“后端开发职能”，“完成项目交付”才会涨。

完成情况：新增 `FunctionCapabilityAttributionAgent`。它先用 Java 判断是否存在实现、交付、负责、设计、部署、组织、运营、调研、测试等真实职责信号；纯课程学习或 Coach 日志直接不进入 LLM 职能归因。通过门禁后，LLM 只能在 Stage 09 候选 ID 中选择最多 1 个 `PRIMARY` 和 2 个 `SECONDARY`，输出相关度、置信度、事实证据与风险标记。每次请求写入 `capability_v2_classification_audits`，当前仍未接线到能力分写入。

### Stage 11：评分引擎接入

把标签相关度、证据质量、活动难度、个人贡献、来源可信度等参数传入 Java AbilityScoreEngine。

目标：一个活动最多影响 3 个知识/职能粗桶，每个桶按相关度和证据强度得到不同分数。细粒度证据不单独加分，只增强对应桶的解释材料和证据质量。

完成情况：新增 `CapabilityV2ScoringService`。它接收已由 Evidence Evaluator 校验的难度、完成质量、个人贡献、各项置信度、证据质量和新颖度，以及知识/职能 Agent 的 `BucketAssignment`：

- 合并两类分配后，全局最多保留 3 个有效桶；若相关度总预算超过 `2.0`，复用 `AbilityFairnessPolicy` 按比例收敛，避免一次经历靠多标签放大总分。
- `PRIMARY` 职能优先保留；`SECONDARY` 的有效相关度按 `0.85` 系数处理，知识桶默认不附加角色系数。
- 每个桶以自己的“调整后相关度 + 归因置信度”进入同一个 `AbilityScoreCalculator`，因此 Java 与 MySQL、知识桶与职能桶会获得不同的经验/能力增量；LLM 仍不直接产出能力分。
- 评分后独立写入 `user_capability_v2_states`、`capability_v2_evidence_links` 和 `capability_v2_score_audits`；审计快照保留原始相关度、预算系数、风险标记、Judge 标记和完整公式输入。
- `COACH_LOG` 等 Stage 06 标记为不可计分的证据会被拒绝，不会静默涨分。现阶段只提供 v2 可调用服务与纯计算预览，不改变旧能力页或既有完成活动主链路；Stage 12 再接 MQ、Outbox 和失败重试。

### Stage 12：幂等写入与异步链路

通过业务 id、证据 id、标签 id 组成幂等键，避免 MQ 重复消费导致重复加分。

要求：失败可重试，重复消息不会重复涨分。

完成情况：复用既有 `domain_event_outbox -> RabbitMQ -> consumer` 基础设施，新增 `capability-v2.score` 路由与持久化队列。完成活动或挑战时仍先创建 `AchievementRecord` 并投递旧的 `ability-evidence.assess` 消息；旧 Evidence Evaluator 成功保存评估后，才通过 Outbox 写入第二条 `CapabilityV2ScoringMessage`，其中固定携带 `recordId / userId / assessmentId / evidenceQuality / novelty`。V2 消费者会校验评估任务确实属于该用户和该成长记录，再执行“个人知识桶归一 -> 核心职能归因 -> Java V2 评分”。

幂等边界已收敛为 `userId + sourceKind + businessSourceId + achievementEvidenceId + bucketId + scoringRuleVersion`：同一完成记录的重复 MQ 消息会在写入前识别为已处理，评分服务按桶复用既有结果；`user_capability_v2_states` 的 `@Version` 继续处理不同完成记录同时更新同一桶时的并发冲突，异常会交给 RabbitMQ 的现有 3 次指数退避重试。为了避免用户更新心得后被误当成第二次完整经历，V2 幂等键不使用可变的心得哈希；心得触发的“更正 / 时间序列回放”将在后续单独实现。

验收：新增消费者编排和评估后投递单测，覆盖“已持久化评估才投递 V2”“重复消息不再次调用分类与评分”“评估信号原样传入 Java 引擎”；Maven 全量测试和隔离端口启动通过。

### Stage 12.1：简历定段接入 V2

完成情况：`ResumeAbilityScoringService` 在把每条面试证据标为 `SCORED` 的事务里，调用 `DomainEventPublisher.publishResumeCapabilityV2Scoring` 写入 Outbox。`CapabilityV2ScoringMessage` 增加 `evidenceSource`（缺省 `ACHIEVEMENT`）与 `resumeEvidenceId`，旧消息兼容。Listener 按来源分发到 `CapabilityV2AsyncScoringService.processResumeEvidence`，它与成长记录共用同一个 `run(...)`。归属校验要求评估就是该简历证据记录的 `abilityAssessmentId`、任务属于同一用户且不挂成长记录。`fromResumeInterviewEvidence` 改为读取面试问题与回答原文，证据状态不再进入哈希；没有回答的证据不计分。

人工验收：后端重启后用一个账号完成一次简历定段，然后：

1. 在 `domain_event_outbox` 中确认每条面试证据都有一条 `capability-v2.score` 消息，payload 里 `evidenceSource=RESUME_INTERVIEW`；

3. 打开“个人成就 -> 能力档案”，确认出现来自简历的知识/职能标签，点开详情能看到证据；
4. 再调用一次评分接口，确认分数不变。

### Stage 13：旧能力迁移预览

### Stage 15：标签详情与里程碑

点击任一标签后展示该标签的证据时间线、评分记录、Judge 状态、重要里程碑。

目标：用户能知道“这个能力为什么是这个分”。

完成情况：新增只读接口 `GET /api/capability-v2/buckets/{bucketId}`（`CapabilityV2BucketDetailService`）。先用 `user_capability_v2_states` 校验该桶属于当前用户，再按 `user_id + bucket_id` 读取证据链接与评分审计，经 `assessment -> job -> achievement_record` 三次批量查询补齐活动标题和心得。里程碑不落库，而是按评分顺序回放审计、复用 `AbilityScoreCalculator.rankFor` 和评分服务的晋级规则得到：第一次点亮、晋级、晋级待复核、单次最大成长。接口额外返回对账结果：证据经验增量之和应等于当前经验值，回放出的阶段应等于当前阶段。Flyway V26 为两张表增加 `(user_id, bucket_id, created_at)` 索引。

前端标签改为可点击按钮，打开 `CapabilityBucketDetailDrawer` 抽屉：顶部展示分数、阶段、可信度、能力分轨迹和对账提示；中部为可点击定位的里程碑；下方为证据时间线，每条展示经验增量、能力分变化、事实点、复核或风险标记，以及可展开的评分因子。

已知边界：V2 的 `REVIEW_REQUIRED` 目前只冻结阶段晋级，不会创建 Judge 任务，因此“待复核”暂时没有处理出口，需要后续单独接入 Judge 流程。（已在 Stage 15.1 解决。）

### Stage 15.1：晋级复核与补充说明

完成情况：

- **统一规则**：新增 `RankPromotionPolicy`，作为评分写入、详情回放和复核解锁共用的唯一晋级规则。只有晋级到“成长中”及以上需要复核；分数始终全额计入。只有“开启这次冻结”的那条证据会标为 `REVIEW_REQUIRED`，冻结期间的后续证据正常计分，不再重复触发，修复了“过 30 分后永久锁死”的问题。
- **标签列表**：画像接口为每个标签返回 `promotionPending / pendingRank`，仅由状态行推导，不额外查询；前端在标签上显示黄色感叹号。
- **详情接口**：返回 `promotion`，包括是否待晋级、目标阶段、开启冻结的证据、进行中的复核、能否发起、冷却截止时间和复核历史。回放把“通过的复核”也作为改变阶段的事件，新增里程碑类型 `REVIEW_PASSED`。
- **复核流程**：新增 `capability_v2_promotion_reviews` 表（Flyway V27），用 `open_key` 唯一索引保证同一标签同时最多只有一个进行中的复核。
  - `POST /api/capability-v2/buckets/{id}/promotion-review`：发起复核并出题。
  - `POST /api/capability-v2/promotion-reviews/{id}/submit`：提交回答并判卷。
- **出题与判分**：3 道题，前两道围绕本人经历，优先使用开启冻结的那条证据；第三道是相关延伸问题，知识标签和职能标签各有侧重。判分沿用 V1 的 `JudgeDecisionPolicy`：70 分及以上通过，50 分以下不通过，中间分数暂不下结论。
- **结果处理**：
  - 通过：阶段直接更新为当前分数对应的阶段，并按 V1 规则调整画像可信度。
  - 不通过：阶段不变，需补充新经历或等待 7 天后才能再试。
  - 模型不可用：不改任何数据，可以立刻重试。
- **复用与重构**：V1 的答案校验、题目清洗和判分钳制抽取为 `JudgeRubricSupport`，V1 和 V2 共用。

人工验收：后端重启（执行 V27）后，找一个能力分 ≥ 30 但阶段仍为“基础”的标签：

1. 确认标签上有黄色感叹号；点开后横幅和“卡住晋级”的证据都能定位到同一条经历。
2. 点击“补充说明”，确认前两题点名了自己的经历。
3. 认真作答通过后，确认阶段直接更新、感叹号消失，并出现“复核通过”里程碑。
4. 再用敷衍的回答测试一次，确认不通过后按钮变为冷却提示。

人工验收：后端重启（会执行 V26）后，用拥有 V2 评分记录的账号点击任一知识或职能标签，确认时间线条数与标签证据数一致、对账提示为绿色、里程碑点击能定位到对应证据；手机宽度下抽屉占满屏幕且无横向滚动。

### Stage 16：Prompt Golden Set 与回归测试

建立 30 到 50 条固定样例，覆盖常见活动、挑战、日志、简历片段。

完成情况（与 Stage 17 合并完成）：

- **三种模式**：
  - `DETERMINISTIC`：只评测门禁和召回，不调模型，已纳入 Maven，与基线对比；
  - `LIVE`：调用真实模型，同时录制 cassette；
  - `REPLAY`：回放 cassette，不调模型，已纳入 Maven，与基线对比。
- **评分**：每条失败样例都会归因到具体环节：`GATE_ERROR`（门禁）/ `RECALL_MISS`（召回）/ `DROPPED_BY_VALIDATION`（被 Java 校验拦下）/ `LLM_WRONG`（模型选错）/ `MODEL_UNAVAILABLE`（模型不可用）。
- **接口**：开发接口 `GET /api/capability-v2/eval/golden-set?mode=...`，默认关闭，需要设置 `CAPABILITY_V2_EVAL_ENABLED=true`。
- **首轮基线**：
  - 知识归一：prompt v1.2 在同一批 36 条可比样例上的正确率为 92%（v1.1 为 83%）；漏合并和过度合并均为 0；注入 3/3 抵御。
  - 职能归因：交付门禁准确率 73.7%，候选召回率@10 为 56%。模型本身只错 2 条，瓶颈在门禁和召回。

### Stage 17：Agent Trace 与问题日志

完成情况：

- **Agent 拆分**：知识归一和职能归因都拆成 `decide`（调模型，不开事务）/ `validate`（纯函数）/ `apply`（只写库）三段。

- **模型故障不再丢分**：模型不可用时抛出 `CapabilityModelUnavailableException`，Listener 通过 Outbox 延迟重投（1 分钟起指数退避，最长 60 分钟，最多 8 次）；模型被关闭时不重试。
- **过滤可追溯**：每一次 Java 过滤都记录为 `CapabilityProposalDrop`（14 种原因）；相关度缺失时直接丢弃，不再默认填 0.5。
- **其他修复**：新增近义后缀重定向；学生文本作为非指令数据传入模型；不复活已停用的同名标签；复用时 `supportCount` 加一；名称过长直接拒绝而不是截断。
- **Trace**：每处理一条完成记录生成一个 `CAPABILITY_V2_PIPELINE` run，包含 6 个步骤及其 artifact。Flyway V28 为分类审计、证据链接、评分审计增加 `agent_run_id`；详情页显示追踪编号。
- 问题记录见 `PROBLEM_LOG.md` 第 056–060 条。
